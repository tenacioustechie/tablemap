# ADR 0027: Initiative as campaign state; strip visibility as presentation

Status: accepted in part (T109: the model, the ops and the schema; amended by T110: the DM's Turns tab over these ops and the DM canvas's turn ring — see "The DM's Turns tab" below). T111 adds the player strip and the players' turn ring and completes this record with the strip's presentation flag. Amends ADR 0020 and ADR 0022 (T110: a seventh tab on `7`, and the turn keys). Numbered 0027 because 0025 and 0026 went to the wall tools and the visibility maths (see ADR 0026's status line): the backlog's T109–T111 call this record "ADR 0026".

## Context
v2 adds an initiative tracker (`docs/plans/2026-09-v2-vision-and-depth.md` §1): entries of a name and a value, optionally linked to a token, advanced turn by turn and round by round from the DM view (T110), and shown to the players as a strip along the TV's edge with a ring around the current token (T111). The questions for T109 were where the list lives (per map, per campaign, or as DM-only UI state), how it changes, what the player may know of it, and how the turn and the round behave at the edges of the list.

## Decision
- **Initiative is campaign state, in `SharedState.initiative`**: `Initiative = { entries: InitiativeEntry[]; turn: number | null; round: number }` with `InitiativeEntry = { id, name, value, tokenId: string | null }` (`state/initiative.ts`; schema v11, v10 documents migrate with `{ entries: [], turn: null, round: 1 }`). Per campaign rather than per map: a fight outlasts a scene switch (the goblins flee downstairs onto the next map) and the order must survive it. In the document rather than in DM UI state: it autosaves, exports, survives a reload of either window and reaches a late player in its snapshot like everything else the player draws. `turn` is an index into the list, not an entry id: the order *is* the list, next and prev step through it, and the ops keep the index on the right entry whenever the list changes (null = nobody's turn yet, always null for an empty list). Rejected: per-map lists — a scene switch would lose or split the fight. Rejected: DM-only state pushed like the presentation — a reload would lose the order, and the list is data the DM builds, not a view setting.
- **A link names a token id on any map, and may dangle.** `map/token-remove` unlinks the entries that named the removed token — unless another map still holds a token with that id, since `duplicateMapScene` copies token ids — but a map removal or a campaign replace does not chase links: consumers read an id that names no token as unlinked (`linkedToken(shared, entry)` → `{ map, token } | null`, searching the active map first, then every map in order). Rejected: cascading every op that can make a token disappear into the initiative — it spreads initiative knowledge over the reducer for a state consumers must tolerate anyway (an imported or hand-edited document can dangle too). Rejected: removing an entry with its token — a monster whose token was deleted by mistake still has its turn.
- **Nine small, pure ops**, reduced by `applyInitiativeOp` and delegated to from `shared.ts: applyOp`: `initiative/add { entry }` (appends; the turn is untouched; a duplicate id is ignored), `initiative/update { id, patch }` (in place, never re-sorts), `initiative/remove { id }`, `initiative/sort` (by value, highest first, stable; the current entry stays current), `initiative/next`, `initiative/prev`, `initiative/set-turn { id | null }` (the round is untouched), `initiative/reset` (the first entry's turn, round 1) and `initiative/clear`. Sorting is its own op, not a side effect of add or update: the DM enters values in any order and sorts once, and a value changed mid-fight (a delayed action) must not move the list under them. At the edges: `next` from the last entry wraps to the first and bumps the round; `prev` from the first wraps to the last and takes the round back, never below 1; `next` with no turn starts at the first entry in the same round, and `prev` with no turn does nothing; removing the current entry hands the turn on exactly as `next` would — to the entry after it, or, when it was the last, to the first entry in the next round — and to nobody when the list empties. Every op returns the same object when it changes nothing, so the store, autosave and sync treat its no-ops as they treat every other op's.
- **Everything goes to the player unfiltered.** The strip needs the names, the order, the turn and the round, and the ring needs the link: the list is in every snapshot and the `initiative/*` ops pass `opsForPlayer` by identity. An entry linked to a hidden token is on the wire too; as with hidden tokens themselves (ADR 0015), the player holds the data and T111 decides what it draws.
- **Whether the strip shows is presentation, not state** (T111 completes this): a per-session toggle carried in `PlayerPresentation` like the overview override, so showing or hiding the strip neither changes the document nor autosaves, and the list itself stays the same data whether or not the players currently see it.

### The DM's Turns tab (T110)
- **The panel is a view over the ops, with no actions module.** Every control of `dm/InitiativePanel.tsx` is exactly one `initiative/*` op dispatched straight to the store; the panel keeps only the add form's draft and which inline confirm (Reset, Clear) is pending, so whatever it shows comes back from the store — and a reload, or the player's strip, sees the same list. Rejected: an `initiativeActions` layer like the tokens' — there is no storage, no asset and nothing to check that the op guards do not. As with walls, nothing is undoable: the order is cheap to fix by hand and has no fog log to share.
- **Turns sits after Tokens but answers to `7`.** Combat is play, next to the tokens its entries link, so the tab goes there in the strip; the digit is the next free one, from a `TAB_KEYS` table in `dm/shortcuts.ts`, so no key a DM has learnt moves. Rejected: numbering by strip order (Draw would become `5`, Walls `6`, Table `7`) — three keys silently changing meaning.
- **`.` is next and `,` previous, only while Turns is the chosen tab** (a folded sidebar with Turns chosen counts). They are ordinary `SHORTCUTS` rows (group `Turns`), so the cheat sheet and the user guide list them; `DmView`'s listener skips them — no dispatch, no `preventDefault` — on any other tab. Space stays the pan override (ADR 0022). Rejected: global turn keys — a stray `.` would move the turn on the TV's strip (T111) while the DM is busy on another tab.
- **Adding from a token** lists the active map's tokens only (the picker is about the scene in front of the DM; a link may still name any map), names the entry `tokens.ts: tokenLabel(token)` — the token list's label, so an unnamed token becomes "Token 3" — takes the drafted value or 0, and disables tokens already linked so a double pick cannot add a monster twice. An empty value field adds 0, and an edited value is only dispatched when it is a finite number, so clearing the field to retype it changes nothing.
- **The DM's turn ring is DM chrome in `DmCanvas`'s controls layer**, derived on every render from `currentEntry` and the *active* map's tokens (not `linkedToken`'s search of every map: the ring can only be drawn where the token is shown). It does not listen, so a click or drag on the ringed token still reaches the token, and it follows the store: the next turn, a move or resize on drop, a map switch, a removed token (whose entries T109 unlinks). T111 draws the players' ring on the shared stage.

## Consequences
- Schema bump to 11 (the migration adds the empty initiative). `isSharedState` requires a well-formed initiative: every entry well-formed with a distinct id, a turn inside the list or null, a whole round of 1 or more; `isSharedOp` delegates the nine kinds to `isInitiativeOp`.
- `map/token-remove` gains its first effect outside its own map: unlinking initiative entries.
- No asset is involved: `referencedAssetIds` and `remapAssetIds` are unchanged, and exports carry the list in `campaign.json`.
- No undo. T110 built the DM tab and its turn ring on these ops and `currentEntry` / `linkedToken`: the sidebar has seven tabs, `ShortcutCommand` gains `turn` and `ShortcutGroup` `Turns`, `TAB_KEYS` decouples the tab digits from the strip's order, and `tokenLabel` moved from the token panel to `state/tokens.ts`. T111 adds the strip, the ring on the shared stage and the presentation flag.
