# ADR 0027: Initiative as campaign state; strip visibility as presentation

Status: accepted (T109: the model, the ops and the schema; amended by T110: the DM's Turns tab over these ops and the DM canvas's turn ring — see "The DM's Turns tab" below; completed by T111: the players' strip, the turn ring moved onto the shared stage and the strip's presentation flag — see "The players' strip and the ring" below). Amends ADR 0020 and ADR 0022 (T110: a seventh tab on `7`, and the turn keys) and ADR 0014 (T111: a presentation field and a layer between the scene and the splash). Numbered 0027 because 0025 and 0026 went to the wall tools and the visibility maths (see ADR 0026's status line): the backlog's T109–T111 call this record "ADR 0026".

## Context
v2 adds an initiative tracker (`docs/plans/2026-09-v2-vision-and-depth.md` §1): entries of a name and a value, optionally linked to a token, advanced turn by turn and round by round from the DM view (T110), and shown to the players as a strip along the TV's edge with a ring around the current token (T111). The questions for T109 were where the list lives (per map, per campaign, or as DM-only UI state), how it changes, what the player may know of it, and how the turn and the round behave at the edges of the list. T111's were where on the TV the strip goes and how it survives a turned view, what it may show, and how one ring can serve both windows without giving a hidden token away.

## Decision
- **Initiative is campaign state, in `SharedState.initiative`**: `Initiative = { entries: InitiativeEntry[]; turn: number | null; round: number }` with `InitiativeEntry = { id, name, value, tokenId: string | null }` (`state/initiative.ts`; schema v11, v10 documents migrate with `{ entries: [], turn: null, round: 1 }`). Per campaign rather than per map: a fight outlasts a scene switch (the goblins flee downstairs onto the next map) and the order must survive it. In the document rather than in DM UI state: it autosaves, exports, survives a reload of either window and reaches a late player in its snapshot like everything else the player draws. `turn` is an index into the list, not an entry id: the order *is* the list, next and prev step through it, and the ops keep the index on the right entry whenever the list changes (null = nobody's turn yet, always null for an empty list). Rejected: per-map lists — a scene switch would lose or split the fight. Rejected: DM-only state pushed like the presentation — a reload would lose the order, and the list is data the DM builds, not a view setting.
- **A link names a token id on any map, and may dangle.** `map/token-remove` unlinks the entries that named the removed token — unless another map still holds a token with that id, since `duplicateMapScene` copies token ids — but a map removal or a campaign replace does not chase links: consumers read an id that names no token as unlinked (`linkedToken(shared, entry)` → `{ map, token } | null`, searching the active map first, then every map in order). Rejected: cascading every op that can make a token disappear into the initiative — it spreads initiative knowledge over the reducer for a state consumers must tolerate anyway (an imported or hand-edited document can dangle too). Rejected: removing an entry with its token — a monster whose token was deleted by mistake still has its turn.
- **Nine small, pure ops**, reduced by `applyInitiativeOp` and delegated to from `shared.ts: applyOp`: `initiative/add { entry }` (appends; the turn is untouched; a duplicate id is ignored), `initiative/update { id, patch }` (in place, never re-sorts), `initiative/remove { id }`, `initiative/sort` (by value, highest first, stable; the current entry stays current), `initiative/next`, `initiative/prev`, `initiative/set-turn { id | null }` (the round is untouched), `initiative/reset` (the first entry's turn, round 1) and `initiative/clear`. Sorting is its own op, not a side effect of add or update: the DM enters values in any order and sorts once, and a value changed mid-fight (a delayed action) must not move the list under them. At the edges: `next` from the last entry wraps to the first and bumps the round; `prev` from the first wraps to the last and takes the round back, never below 1; `next` with no turn starts at the first entry in the same round, and `prev` with no turn does nothing; removing the current entry hands the turn on exactly as `next` would — to the entry after it, or, when it was the last, to the first entry in the next round — and to nobody when the list empties. Every op returns the same object when it changes nothing, so the store, autosave and sync treat its no-ops as they treat every other op's.
- **Everything goes to the player unfiltered.** The strip needs the names, the order, the turn and the round, and the ring needs the link: the list is in every snapshot and the `initiative/*` ops pass `opsForPlayer` by identity. An entry linked to a hidden token is on the wire too; as with hidden tokens themselves (ADR 0015), the player holds the data and T111 decides what it draws (below: every name in the strip, but a ring only round a token the players can see).
- **Whether the strip shows is presentation, not state** (completed by T111): `PlayerPresentation.initiativeStrip` and `PresentationState.initiativeStrip` (`state/calibration.ts`; default false, required by `isPlayerPresentation`, compared by `playerPresentationEqual`, copied through `sync.ts`'s decoder), a per-session switch like the overview override, the blackout and the splash. Showing or hiding the strip dispatches nothing, bumps no seq, is never autosaved or exported, and starts off again when the DM window reloads; the list stays the same data whether or not the players currently see it. The toolbar's **Turn strip** (`initiative-strip-toggle`, `aria-pressed`, after **Show splash**) and the Turns tab's **Show the turn strip on the TV** (`initiative-strip-checkbox`) are two views of this one flag. Rejected: a document field — whether the TV shows the order tonight is not a property of the campaign, and toggling it would churn autosave and the undo-less document. Rejected: a player-side setting — the player window has no chrome and must never decide what it shows.

### The DM's Turns tab (T110)
- **The panel is a view over the ops, with no actions module.** Every control of `dm/InitiativePanel.tsx` is exactly one `initiative/*` op dispatched straight to the store; the panel keeps only the add form's draft and which inline confirm (Reset, Clear) is pending, so whatever it shows comes back from the store — and a reload, or the player's strip, sees the same list. Rejected: an `initiativeActions` layer like the tokens' — there is no storage, no asset and nothing to check that the op guards do not. As with walls, nothing is undoable: the order is cheap to fix by hand and has no fog log to share.
- **Turns sits after Tokens but answers to `7`.** Combat is play, next to the tokens its entries link, so the tab goes there in the strip; the digit is the next free one, from a `TAB_KEYS` table in `dm/shortcuts.ts`, so no key a DM has learnt moves. Rejected: numbering by strip order (Draw would become `5`, Walls `6`, Table `7`) — three keys silently changing meaning.
- **`.` is next and `,` previous, only while Turns is the chosen tab** (a folded sidebar with Turns chosen counts). They are ordinary `SHORTCUTS` rows (group `Turns`), so the cheat sheet and the user guide list them; `DmView`'s listener skips them — no dispatch, no `preventDefault` — on any other tab. Space stays the pan override (ADR 0022). Rejected: global turn keys — a stray `.` would move the turn on the TV's strip (T111) while the DM is busy on another tab.
- **Adding from a token** lists the active map's tokens only (the picker is about the scene in front of the DM; a link may still name any map), names the entry `tokens.ts: tokenLabel(token)` — the token list's label, so an unnamed token becomes "Token 3" — takes the drafted value or 0, and disables tokens already linked so a double pick cannot add a monster twice. An empty value field adds 0, and an edited value is only dispatched when it is a finite number, so clearing the field to retype it changes nothing.
- **The DM's turn ring** was DM chrome in `DmCanvas`'s controls layer, derived on every render from `currentEntry` and the *active* map's tokens (not `linkedToken`'s search of every map: the ring can only be drawn where the token is shown). Superseded by T111, which draws one ring for both windows on the shared stage (below); the canvas still derives the token id the same way and still reports it as `data-turn-ring`.

### The players' strip and the ring (T111)
- **The strip is a DOM layer turned with the view, not a stage layer.** `player/InitiativeStrip.tsx` renders the list as chips (`player-initiative-entry`, the current one `data-current="true"` and `aria-current="step"`, filled with the ring's gold) and "Round n" pinned at the end (`player-initiative-round`), at the top of a `Rotated` box — the one the idle title and the splash already use — inside its own absolutely placed layer (`player-initiative-layer`, z-index 5). So it runs along the top of the picture *as the players read it* whichever way the view is turned, sits over the scene and under the splash (10) and the blackout (20), which cover it like everything else, and appears the instant a delta lands with no stage redraw. Rejected: text on the Konva stage — it would be under the fog, scaled with the map and turned with the map's own rotation. Rejected: a fixed physical TV edge — after a half turn the players would read it upside down, while the title and splash beside it read the right way up.
- **Thin by construction.** The strip is `INITIATIVE_STRIP_VMIN` (7) % of the display's *shorter* side thick (`vmin`), so it covers less than 8 % of the display's height at every rotation and on any display shape, without measuring anything; its text is `vmin`-sized too. A list longer than the edge scrolls sideways (no scrollbar), and a layout effect scrolls the current chip to the middle whenever the turn or the list changes — `stripScrollLeft({ chipLeft, chipWidth, viewWidth, contentWidth })`, pure and clamped, fed layout offsets rather than bounding boxes, which the rotation turns. The overview badge, at the display's top-right, steps out of the strip's way (margins of the strip's thickness) while the strip shows.
- **When it shows**: the DM's switch is on, the player is synced, the list is not empty, and the ruler screen is not up (the DM is measuring). With no map shown it still runs over the idle title: the fight is campaign state.
- **Every entry is named.** The strip draws the list the DM built, including entries linked to hidden or fogged tokens, and the current highlight follows the turn wherever it is. Rejected: leaving out entries whose token the players cannot see — the highlight would jump or vanish on that monster's turn, telling the players as much as the name. The DM controls it the way they control the list: add the ambusher when it appears, give it a name that gives nothing away, or keep the strip off.
- **One ring on the shared stage, by the players' rules.** `map/TokenLayer.tsx` rings the token named by `turnTokenId` — `currentEntry(initiative)?.tokenId`, which `DmCanvas` and `PlayerView` each derive from their own copy of the shared state and hand to `MapStage` — when that view draws the token: `turnRingToken(tokens, view, visibility, id)` is the token on the DM whatever its state, and on the player only while it is `visible` (not hidden, no fogged cell). The ring is a non-listening gold `Circle` (`TURN_RING_COLOR`; name and id `turn-ring`, attr `data-testid`, `data-token-id`) round the footprint with a `TURN_RING_GAP_PX` (4) screen-pixel gap, `TURN_RING_WIDTH_PX` 3 screen px on the DM and 5 on the TV (seen from across the table); `MapStage` reports the ringed id as `data-turn-ring`. It is drawn after every token as a child of the layer, not of the token's group: no neighbour covers it and a hidden token's DM opacity does not fade it. There is no presentation flag: the ring is part of the scene, like the tokens, and follows every delta. Like a token, it moves on the drop, not during a DM drag. Rejected: keeping T110's controls-layer ring for the DM and adding a player ring — two drawings of one thing whose rules could drift. Rejected: a ring round a hidden or fogged token on the TV — it would give the token's position away.

## Consequences
- Schema bump to 11 (the migration adds the empty initiative). `isSharedState` requires a well-formed initiative: every entry well-formed with a distinct id, a turn inside the list or null, a whole round of 1 or more; `isSharedOp` delegates the nine kinds to `isInitiativeOp`.
- `map/token-remove` gains its first effect outside its own map: unlinking initiative entries.
- No asset is involved: `referencedAssetIds` and `remapAssetIds` are unchanged, and exports carry the list in `campaign.json`.
- No undo. T110 built the DM tab and its turn ring on these ops and `currentEntry` / `linkedToken`: the sidebar has seven tabs, `ShortcutCommand` gains `turn` and `ShortcutGroup` `Turns`, `TAB_KEYS` decouples the tab digits from the strip's order, and `tokenLabel` moved from the token panel to `state/tokens.ts`.
- T111: the `presentation` message carries a ninth field, required by the guard; both windows come from the same build, so `PROTOCOL_VERSION` stays as it was for T009's fields. `MapStage` gains `turnTokenId` and `data-turn-ring`; `TokenLayer` gains the ring, `turnRingToken` and the ring constants, which left `dm/DmCanvas.tsx` (its controls layer no longer draws a ring); `player/` gains `InitiativeStrip.tsx` and the root's `data-initiative-strip`; the toolbar gains a third override switch.
