# ADR 0023: Collapsible sidebar and folded setup forms, session facts in the toolbar, and the TV rotation remembered per display

Status: accepted (T019). Amends ADR 0011 (a second per-display settings row), ADR 0014 (its "per-display rotation" follow-up) and ADR 0020 (the collapse toggle in the tab strip).

## Context
The tabbed sidebar (ADR 0020) and the shortcuts (ADR 0022) fixed reach; what was left of the DM usability review (`docs/plans/2026-09-dm-usability.md` §1, items 5 and 6, and §3.5) was orientation and room. The 260 px sidebar was tight for the map list and the token editor, yet on a laptop the DM sometimes wants all of the screen for the canvas. Two setup-once forms — the blank-map form and calibration's TV-size fieldset — took permanent space on the two tabs that host the map list and the calibration status. The two facts a DM checks most between tabs, *which map the TV is showing* and *whether the TV is calibrated*, were only visible on the Maps and Table tabs. And the player view rotation was forgotten on reload: a TV mounted the other way round had to be turned every evening, which ADR 0014 listed as the obvious follow-up.

## Decision
- **Sidebar 300 px, collapsible from the tab strip, remembered next to the tab.** `SidebarTabs` gains the toggle (`sidebar-toggle`, `aria-expanded`). Collapsed, the sidebar is a 44 px strip of tab initials (each tab keeps its accessible name), the tablist is vertical, and **no tab panel is mounted** — the same "one answer per tab" rule as ADR 0020, now including "none". Choosing a tab expands the sidebar, whether by click, arrow key, the `1`–`5` keys or a toolbar chip; a *tool* key (`B`, `P`, …) only records the tab, because a DM who folded the sidebar to see the map and then reaches for the brush did not ask for the sidebar back. The state lives in `localStorage` under `tablemap.dm.sidebar`, DM-window UI state exactly like the tab (ADR 0020), with the same guards. The width is not user-draggable: one open width and one collapsed width are enough, and a free width would need a third remembered value and a resize handle for little gain. The canvas follows through the grid column; `useContainerSize` already remeasures on any resize.
- **Setup-once forms fold behind disclosures.** The blank-map form sits behind **New blank map**, closed by default, with the import picker left visible (dropping or picking an image is the common path). Calibration's TV-size fieldset is open while the display is uncalibrated — it is one of the two ways in, and a first-time DM must see both — and folds behind **Recalibrate from the TV size** once a calibration exists. Both are local component state (they reset with the panel, like the drafts inside them), not remembered: a folded form is the wanted default every time. Rejected: `<details>` — its toggle event and styling are uneven across browsers and it cannot be forced open by state; a button with `aria-expanded` over a conditionally rendered form is the same pattern the rest of the DM view uses.
- **The toolbar shows the active map's name and a calibration chip**, between the splash switch and the tool chip: `active-map-name` ("No map shown" without one) and `calibration-chip` ("1 inch = 96 px/in" from the current calibration and cell unit, or "Not calibrated"), the latter a button that opens the Table tab. The text comes from a pure `describeCalibration` next to `describeTool`, for the same reason: testable without React and one place for the wording. They are derived from the store on every render, so they are live by construction.
- **The TV rotation is a per-display settings row, a sibling of the calibration, not a field in it.** `settings` rows `rotation:<displayKey>` hold `{ rotation, updatedAt }` (`DisplayRotation`, `state/calibration.ts`; `getDisplayRotation` / `setDisplayRotation` in `persistence.ts`, 0 deleting the row so "no record" and "0" are one state). The `CalibrationSession` loads it with the calibration whenever the player reports a display (stale loads dropped by their own generation counter), puts an unknown display at 0, and writes every change to `presentation.rotation` under the connected display's key; a turn made while no display is known is not saved and is replaced by the display's own value when it connects (the rotation belongs to the display, and only a connected display can own it). A DM turn made while a load is still in flight wins over the load. Rejected: adding `rotation` to `DisplayCalibration` — clearing the calibration must not clear the rotation (a TV stays mounted the way it is), the strict `isDisplayCalibration` guard would have to accept records with and without the field, and the two values change at different times for different reasons; a separate row costs one more read per display report and nothing else. Rejected: resetting the rotation in the store's `setPlayerDisplay` the way the calibration is reset — the session's save-on-change would then write that reset under the new display's key before its own value loaded. The store is untouched; the session owns both directions. Export / import are unaffected: settings are per machine (ADR 0011).

## Consequences
- No store, protocol or schema change; the player is untouched. `SidebarTabsProps` gains `collapsed` / `onCollapsedChange`.
- Every unit and e2e test that fills the blank-map or TV-size form opens the disclosure first through one helper per side (`src/test/dmPanels.ts`, `e2e/helpers.ts`), a mechanical change like ADR 0020's `openTab`; no assertion was weakened.
- A TV that was turned once stays turned across reloads and player-window reopenings; a different display (or a rearranged layout, which changes the display key — ADR 0011) starts at 0° and needs its own turn. The turn is not part of an export, like the calibration.
- The sidebar's collapsed state is remembered per browser like the tab, so a DM who folded it for a session finds it folded next time; the first tab click opens it.
