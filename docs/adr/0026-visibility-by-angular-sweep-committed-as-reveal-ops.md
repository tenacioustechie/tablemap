# ADR 0026: Visibility by angular sweep; committed as ordinary reveal ops

Status: proposed (T104). The maths (`map/visibility.ts`) is accepted and in the code; T106 completes this record with the reveal on drop and the door re-run, T107 amends it with the derived overlay. Numbered 0026 because T102 used 0025 for the wall tools (ADR 0025): the backlog's T104–T108 call this record "ADR 0025", and the initiative record T109 plans as "ADR 0026" takes the next free number.

## Context
v2's vision (`docs/plans/2026-09-v2-vision-and-depth.md` §1–2): a token with a vision radius reveals what it can see; walls and closed doors block, open doors do not. Both windows need the same answer from the same shared data (ADR 0024) — the DM to commit a reveal when a token is dropped (T106), both to draw what is currently seen (T107) — so the computation must be pure, deterministic and cheap enough to run on every pointer move of a drag preview, and for every seeing token when a door is toggled. Maps carry tens to a few hundred segments at any angle; radii are a few to a dozen cells, i.e. hundreds of map pixels.

## Decision
- **What a point sees is a polygon, computed by an angular-sweep raycast**: `visibilityPolygon(origin, radiusPx, segments, bounds)` → flat `[x0, y0, …]` in map pixels, star-shaped about the origin. Rays are cast just either side (±1e-5 rad) of every segment endpoint and map corner inside the radius — the directions where what a ray hits can change — at every point where a segment or a map edge crosses the radius circle, and at 64 fixed angles round the circle (`RADIUS_STEPS`; an open area is a 64-gon, 0.16 % short of the circle's area). Each ray keeps its nearest hit: a segment, the map's edge (the bounds are four implicit segments, met by a slab test) or the radius. The hits, sorted by angle, are the polygon. Rejected: grid field-of-view (shadow casting over cells) — it ties vision to square cells, which the plan keeps out of v2 (hex is T113), and cannot honour a diagonal wall or a doorway off the grid; a per-pixel raster — slow on a 4096 px map and it yields pixels, not a shape the fog log can store; shadow quads per wall merged by polygon booleans — needs a clipping library (a new dependency) and is more fragile at shared corners; an exact sweep with an ordered set of active segments — the same polygon up to the circle's chords for noticeably more, and more delicate, code, when the raycast below meets the budget with room to spare.
- **Blocking is `blockingSegments(walls)`: every wall, and every door while it is closed** (`isBlocking`). An open door is no segment at all, so opening one gives exactly the polygon of a map without it.
- **Degenerate cases never throw, and never make a token see less than it should.** A segment passing through the origin (within 1e-3 px) blocks nothing: a 2 × 2 token's centre is a grid corner, where walls drawn along grid lines meet, and it must see both sides rather than nothing. A segment seen edge-on blocks nothing (walls have no thickness). Collinear segments that meet or overlap leave no gap: a ray through a shared endpoint counts as hitting it (1e-9 slack on the segment parameter). Segments beyond the radius, of zero length or with non-finite coordinates are ignored. No radius, an origin that is not a finite point on the map, and an empty map give `[]` — which T106 commits as nothing, since a `polygon` fog shape needs three points.
- **Fast by pruning, not by a cleverer algorithm.** Each ray only tests the segments in its angular bin (256 bins, one bin of margin either side; a segment subtending more than 0.9π, i.e. very close to the origin, goes in every bin), nearest first, and stops once the next candidate starts beyond its best hit. The budget — 400 blocking segments, one origin, under 4 ms on Node — is a unit test over two scenes: scattered walls, and radial spokes that defeat the nearest-first pruning and leave it to the bins.
- **Deterministic by construction.** The output depends only on the input values, not on segment order: the ray angles are a sorted list of numbers and each hit is a minimum. Both windows therefore compute identical polygons from identical shared state.
- **What a token sees is committed as an ordinary reveal op** (plan §1; implemented by T106, which completes this section): a drop commits the polygon as one `shape` op with a `polygon` shape in `reveal` mode, and a door toggle re-runs vision for every seeing token and dispatches those ops in one `dispatch`. The fog log stays authoritative (ADR 0012): undo, sync, compaction and export need nothing new, and the op is the shape the lasso already produces. "Currently visible" is never stored; each window derives it from the same polygons (T107).

## Consequences
- `map/visibility.ts` is pure: it imports `state/walls`, `map/geometry` and types from `map/viewport`, reads wall endpoints only through `segmentPoints` (the boundary test still finds no endpoint read in `src/map/`), and is unit-tested against a brute-force sight-line check. T104 changes no store, schema, UI or wire format.
- The origin is a token's centre and the radius `visionRadiusPx(vision, cellSize)`; choosing the centre, and anything about token footprints, is T106's.
- Where the radius is the limit, the edge is a chord of the circle, at most 0.12 % of the radius inside it (a third of a pixel at 280 px).
