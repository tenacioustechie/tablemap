# ADR 0026: Visibility by angular sweep; committed as ordinary reveal ops

Status: accepted (T104, T106). The maths (`map/visibility.ts`) is in the code; T106 completed this record with the reveal on drop, the door re-run and the drag preview (the last Decision bullet, and the T106 amendment below); T107 amends it with the derived overlay. Numbered 0026 because T102 used 0025 for the wall tools (ADR 0025): the backlog's T104–T108 call this record "ADR 0025", and the initiative record T109 plans as "ADR 0026" takes the next free number. Amended by T105 (below): the vision fields — `Token.vision`, `MapScene.visionDim`, `map/set-vision-dim` and `state/vision.ts` — and schema v10. Amended by T106 (below): `state/visionActions.ts`, `tokenVisionPolygon`, one undo step per dispatch in `fogHistory.ts`, and the DM canvas's drag preview.

## Context
v2's vision (`docs/plans/2026-09-v2-vision-and-depth.md` §1–2): a token with a vision radius reveals what it can see; walls and closed doors block, open doors do not. Both windows need the same answer from the same shared data (ADR 0024) — the DM to commit a reveal when a token is dropped (T106), both to draw what is currently seen (T107) — so the computation must be pure, deterministic and cheap enough to run on every pointer move of a drag preview, and for every seeing token when a door is toggled. Maps carry tens to a few hundred segments at any angle; radii are a few to a dozen cells, i.e. hundreds of map pixels.

## Decision
- **What a point sees is a polygon, computed by an angular-sweep raycast**: `visibilityPolygon(origin, radiusPx, segments, bounds)` → flat `[x0, y0, …]` in map pixels, star-shaped about the origin. Rays are cast just either side (±1e-5 rad) of every segment endpoint and map corner inside the radius — the directions where what a ray hits can change — at every point where a segment or a map edge crosses the radius circle, and at 64 fixed angles round the circle (`RADIUS_STEPS`; an open area is a 64-gon, 0.16 % short of the circle's area). Each ray keeps its nearest hit: a segment, the map's edge (the bounds are four implicit segments, met by a slab test) or the radius. The hits, sorted by angle, are the polygon. Rejected: grid field-of-view (shadow casting over cells) — it ties vision to square cells, which the plan keeps out of v2 (hex is T113), and cannot honour a diagonal wall or a doorway off the grid; a per-pixel raster — slow on a 4096 px map and it yields pixels, not a shape the fog log can store; shadow quads per wall merged by polygon booleans — needs a clipping library (a new dependency) and is more fragile at shared corners; an exact sweep with an ordered set of active segments — the same polygon up to the circle's chords for noticeably more, and more delicate, code, when the raycast below meets the budget with room to spare.
- **Blocking is `blockingSegments(walls)`: every wall, and every door while it is closed** (`isBlocking`). An open door is no segment at all, so opening one gives exactly the polygon of a map without it.
- **Degenerate cases never throw, and never make a token see less than it should.** A segment passing through the origin (within 1e-3 px) blocks nothing: a 2 × 2 token's centre is a grid corner, where walls drawn along grid lines meet, and it must see both sides rather than nothing. A segment seen edge-on blocks nothing (walls have no thickness). Collinear segments that meet or overlap leave no gap: a ray through a shared endpoint counts as hitting it (1e-9 slack on the segment parameter). Segments beyond the radius, of zero length or with non-finite coordinates are ignored. No radius, an origin that is not a finite point on the map, and an empty map give `[]` — which T106 commits as nothing, since a `polygon` fog shape needs three points.
- **Fast by pruning, not by a cleverer algorithm.** Each ray only tests the segments in its angular bin (256 bins, one bin of margin either side; a segment subtending more than 0.9π, i.e. very close to the origin, goes in every bin), nearest first, and stops once the next candidate starts beyond its best hit. The budget — 400 blocking segments, one origin, under 4 ms on Node — is a unit test over two scenes: scattered walls, and radial spokes that defeat the nearest-first pruning and leave it to the bins.
- **Deterministic by construction.** The output depends only on the input values, not on segment order: the ray angles are a sorted list of numbers and each hit is a minimum. Both windows therefore compute identical polygons from identical shared state.
- **What a token sees is committed as an ordinary reveal op** (plan §1; T106): a drop commits the token's polygon as one `shape` op with a `polygon` shape in `reveal` mode and the standard feather, and a door toggle re-runs vision for every seeing token and dispatches those ops in one `dispatch` — one seq, one delta, one undo step. The fog log stays authoritative (ADR 0012): sync, compaction and export need nothing new, and the op is the shape the lasso already produces; undo needed one DM-side change so that a dispatch of several ops is one step (the T106 amendment). "Currently visible" is never stored; each window derives it from the same polygons (T107).

## Consequences
- `map/visibility.ts` is pure: it imports `state/walls`, `map/geometry` and types from `map/viewport`, reads wall endpoints only through `segmentPoints` (the boundary test still finds no endpoint read in `src/map/`), and is unit-tested against a brute-force sight-line check. T104 changes no store, schema, UI or wire format.
- The origin is a token's centre and the radius `visionRadiusPx(vision, cellSize)`; choosing the centre, and anything about token footprints, is T106's.
- Where the radius is the limit, the edge is a chord of the circle, at most 0.12 % of the radius inside it (a third of a pixel at 280 px).

## Amendment (T105): the vision fields
The data the maths above runs on, without the behaviour: nothing is revealed or dimmed by it until T106 and T107.

- **`Token.vision: number` is the vision radius in whole grid cells, 0 or more; 0 (the default) is no vision.** It is one more field in `TOKEN_FIELD_GUARDS` (`isTokenVision`: a safe integer ≥ 0), so `isToken` and `isTokenPatch` share the rule and a `map/token-update` carries it like any other field — a negative or fractional vision is refused on the wire and in a stored document. Cells, not pixels or feet: the grid is what a DM reads a creature's sight in, a realignment of the grid keeps a token's reach in cells, and `visionRadiusPx(vision, cellSize)` above turns it into map pixels at the moment of use. Whole cells because nobody measures sight in fractions of a square and an integer is unambiguous to compare and to type. **A hidden token keeps its vision**: hiding is about what the players see of the token, not what it sees; the DM decides whether a hidden scout's view is revealed. The model sets no upper bound; the token editor offers 0–60 (`TOKEN_VISION_MAX`) and rounds and clamps what is typed (`clampTokenVision`). Rejected: a separate "has vision" flag next to a radius — two fields that can disagree, where `vision > 0` says it once.
- **`MapScene.visionDim: "auto" | "on" | "off"`, default `auto`, set by `map/set-vision-dim { id, visionDim }`** (ignored for an unknown map, same state when unchanged, unfiltered to the player). It decides whether the player dims revealed areas no token currently sees (T107): **`auto` dims only while any token on the map has `vision > 0`**, `on` and `off` force it. `auto` is the plan's dim rule (plan §1): a map whose fog the DM runs by hand has no seeing token and looks exactly as it did before vision existed, while a map the party explores with vision dims without a setting being touched. The override exists for the cases the rule guesses wrong — a seeing familiar on a map the DM wants undimmed, or a dungeon to be dimmed before the first seeing token is placed. Per map, not per campaign: one campaign mixes battle maps, towns and dungeons. Rejected: no override (the rule alone) — the exceptions above are real; a campaign-wide setting — too coarse.
- **The rule is one pure function, `state/vision.ts: mapUsesVision(scene)`**, next to `seeingTokens(scene)` (the tokens with `vision > 0`, hidden ones included, in document order: the tokens T106 re-runs on a door toggle) and `tokenCentre(token, cellSize)` — **a token sees from the centre of its footprint**, which settles the choice the Consequences above left to T106: the centre is where the token is drawn and what `rotateToken` turns, and a 2 × 2 token's centre on a grid corner is exactly the case the "segment through the origin blocks nothing" rule was written for. Both windows call the same functions over the same shared state, so they cannot disagree about whether a map is dimmed.
- **Schema v10.** The v9 → v10 migration gives every token `vision: 0` and every map `visionDim: "auto"` (values already present are kept): nothing had vision before, and `auto` with nobody seeing dims nothing, so every older map looks the same. The fields are plain document state, autosaved, copied by `duplicateMapScene` and carried in `campaign.json` by export; no asset is involved.
- **The controls exist now, wired to the ops:** the token editor's **Vision (cells)** (`token-vision`) goes through `TokenActions.update`, and the Fog tab's **Dim unseen areas on the TV** (`vision-dim`) dispatches `map/set-vision-dim`, with a hint saying what `auto` resolves to on the shown map. Shipping the settings before the behaviour lets T106 and T107 be pure behaviour changes over data every campaign already has.

## Amendment (T106): reveal on drop, door re-run, drag preview
The behaviour over the fields: what a seeing token sees is revealed when it is dropped, when it is given vision and when a door is toggled; the DM canvas previews it while the token is dragged. No schema, wire or document change.

- **`state/visionActions.ts: createVisionActions(store, { apply?, schedule? })`, on the DM side only.** `revealFor(mapId, tokenId)` appends `visionRevealOp(scene, token)` — `fogShape("reveal", polygonShape(tokenVisionPolygon(scene, token)), fogFeatherPx(cellSize))`, the feather the fog tools use, which moved from `dm/fogTool.ts` to `state/fog.ts` (re-exported) so state code need not import DM UI — and `revealAll(mapId)` does it for `seeingTokens(scene)` in **one** `apply` call. The DM view passes `FogActions.apply`, now variadic (`apply(mapId, ...ops)`: one dispatch, then the usual compaction check), so a long session of drops compacts like any other. **`state/vision.ts: tokenVisionPolygon(scene, token, segments?)`** is the pure "what a token sees" that the reveal, the preview and T107's overlay share: `visibilityPolygon(tokenCentre(token), visionRadiusPx(vision, cellSize), blockingSegments(walls), scene)`, `[]` without vision (and so no op: a `polygon` needs three points).
- **Triggers are read off the op stream (`store.onOps`), not wired into each control.** A `map/token-update` whose patch has `x` or `y` — what `TokenActions.move` dispatches on a drop, and a resnap, which moves the token too — or a `vision` above 0 queues that token; a `map/door-set-open`, open or closed, queues every seeing token of its map. Nothing else triggers: not `map/set-active` (a map switch), not `campaign/replace` (a load: the log already holds what was seen), not `map/token-add`, not wall edits. So the canvas drag, the token editor, the canvas door click and the Walls panel's door toggle all trigger it with no code of their own, and the player, which never dispatches, never does. Rejected: calling `revealFor` from `DmView`'s drag and door callbacks — three call sites in two components to keep in step with the triggers.
- **The reveal runs after the triggering dispatch, never inside it.** Op listeners run synchronously in registration order; a dispatch from inside one would reach the listeners registered after it — the sync publisher among them — before the op that caused it, so the player would get seq n + 1 before n. Triggers are queued per map and flushed by `schedule`, a microtask by default (before any paint or input event): a drop and a door toggle in the same tick make one reveal dispatch. **Feedback guard:** while the actions' own `apply` runs, their listener ignores every op, so nothing a reveal sets off can trigger another reveal.
- **One dispatch, one undo step.** `map/fog-undo` drops one op, so `fogHistory.ts` now records, while started, each map's multi-op groups — where a group ends in the map's history (`fogOpsFrom + fogOps.length`, which a compaction does not move) and how many ops it holds. `undo` drops a whole group with that many `map/fog-undo` ops in one dispatch and puts the group on the redo stack as one entry; `redo` re-appends it with one `apply` call. The player applies n plain undos, and nothing is stored: the groups are DM bookkeeping, so after a reload every op is a step again, a group partly baked by a compaction undoes what is left of it, and a group undone some other way is forgotten. Rejected: a `polygons` fog shape carrying every token's polygon in one op — a new shape kind for the rasteriser, the guards, map rotation and snapping, to answer a history question; a `count` on `map/fog-undo` — a wire change for what n undos in one delta already say.
- **A reveal that changes nothing is skipped** (`alreadyRevealed(log, op)`): when a reveal-all, or an identical polygon reveal with the same feather, follows the log's last op that hides, only reveals come after that op and reveals never take fog back, so the new op would change no pixel. Dropping a token back where it stood, or toggling a door no seeing token looks through, therefore adds no empty undo step. Conservative by design: the baked base is not consulted, and anything after a hide is revealed again.
- **Closing a door re-hides nothing.** It re-runs vision like opening one, and the narrower polygons are reveals too: fog is additive (plan §5, item 3).
- **The drag preview belongs to the DM canvas.** `TokenTool` gains `onDragMove(id, topLeft)`, reporting where the token would land — clamped and snapped like the drop — on every drag move. `DmCanvas` keeps the latest position in a ref and computes `tokenVisionPolygon` at most once per animation frame, drawn like the fog reveal preview: the tint and dashed outline in the overlay (node `vision-preview`) and the shape punched through the fog layer (`vision-preview-reveal`). The drop, arming a tool, holding Space or switching maps drops it; `data-vision-preview` reports its vertex count. Nothing is dispatched until the drop, and the preview is the polygon the drop commits (drawn without the feather). The perf budget holds: T104's 4 ms for 400 segments, at most once per frame, and once more on the drop (`visionActions.test.ts` keeps a drop among 400 walls under 16 ms, median).
- **`state/visionActions` is off-limits to `src/player/**`** (ESLint rule and boundary test), like every module that writes state.
