# ADR 0024: Walls and doors as free segments, shared with the player but never drawn there

Status: accepted (T101). Amends ADR 0020 and ADR 0022 (a sixth sidebar tab, **Walls**, answering to `5`; **Table** moves to `6`). Amended by ADR 0025 (T102): the DM's wall layer is no longer read-only — with no tool armed its nodes listen for selection and the selected segment's ends drag — and the surface reports the segments as well as their count. The model, the ops and the player rule are unchanged.

## Context
v2 (`docs/plans/2026-09-v2-vision-and-depth.md`) adds line-of-sight vision: a token with a vision radius reveals what it can see, walls block, doors let sight through while open, and the player screen dims what no token currently sees. Every one of those needs the same fact about the scene — where the walls and doors are — in both windows: the DM computes the reveal on drop, the player computes the "currently visible" overlay (T107). The question for T101 was what a wall *is* in the document, and whether the player may know about it.

## Decision
- **A wall is a free line segment in map pixels, any angle: `{ id, x1, y1, x2, y2, kind: "wall" }` or `{ …, kind: "door", open }`** (`state/walls.ts`, schema v9 adds `MapScene.walls: WallSegment[]`, v8 documents migrate with `[]`). Segments, not grid edges: printed maps have diagonal walls, curved rooms and doorways that do not line up with the cells, and the grid may be realigned after the walls are drawn. Segments are also what v3's wall tiles will emit (T203), so one format serves both the hand-drawn and the tiled scene; nothing in the model records how a segment came to be. A door is a segment with one flag, not a separate list: the vision maths treats "a closed door" and "a wall" alike (`isBlocking`), and a tool that turns a wall into a door (T102) is a one-field change under the same id. Rejected: per-cell wall bits (four flags per cell) — cheap to store, but useless off-grid and thrown away by a realignment; rejected: polylines — a room's walls are one path only until the first door splits it, and every consumer wants segments anyway.
- **Three ops, one shape: `map/wall-set { id, segment }` (upsert by segment id), `map/wall-remove { id, segmentId }`, `map/walls-clear { id }`.** A door opens and closes through `map/wall-set` too (T103 adds the convenience over it): one op kind to guard, replay and mirror, and a door toggle is then indistinguishable from any other edit for the sync layer, undo (when it comes) and autosave. Rejected: a `map/wall-update` with a patch — the segments are small, whole-value replacement is simpler to reason about on the wire, and `patchWall` exists for callers that want it.
- **Walls travel to the player unfiltered, and no stage ever draws them.** Unlike notes (ADR 0016) the player *needs* walls: the visible-area overlay is computed there from the same data the DM used, so it is right by construction and costs no message. The rule is ADR 0015's for hidden tokens: the player holds the data and simply has no code that would show it. `dm/WallLayer.tsx` draws the segments as DM chrome in the stage's controls layer (solid walls, dashed closed doors, thin open doors, one colour, screen-pixel widths), and `player/boundary.test.ts` asserts that neither `src/map/` nor `src/player/` imports that module or reads a segment's endpoints. Rejected: stripping walls from the wire like notes and sending the *computed* polygons instead — the overlay must update on every token move and door toggle, so the polygons would be recomputed and re-sent constantly, and a late player could not rebuild its picture from a snapshot.
- **`rotateScene` turns both endpoints** with the same point transform as everything else (ADR 0021), so a sideways scan's walls are drawn once and follow the map; four quarter turns are the identity for walls as for the rest.
- **The Walls tab exists from this task**, as a placeholder (the counts and **Clear walls** with an inline confirm), after Draw and before Table, so that T102's tools have a home and the tab order is settled once: `1`–`6` name the tabs, Table moves from `5` to `6`. Rejected: hiding the tab until T102 — it would move Table's key twice.

## Consequences
- Schema bump to 9 (migration adds `walls: []`); three new shared ops that pass `opsForPlayer` unchanged; `sceneRotation.ts` gains `rotateWall`; `duplicateMapScene` copies walls; exports carry them in `campaign.json` (no assets are involved). `referencedAssetIds` is unchanged.
- The DM canvas gets a second piece of DM-only chrome in the controls layer (the note markers were the first); `data-walls` on the surface reports the count.
- `DM_TABS` has six entries; `SidebarTabs`, the tab keys, the cheat sheet and the user guide's table follow from the one list. E2E specs that enumerate the tabs were updated; no new e2e for this task (`e2e: false`).
- T102 adds the drawing tools over these ops, T103 the door click on the canvas and the list in the panel, T104 the visibility polygon over `segmentPoints` / `isBlocking`, T107 the player overlay — none of them changes the model.
