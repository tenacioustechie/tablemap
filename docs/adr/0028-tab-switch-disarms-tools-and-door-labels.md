# ADR 0028: A tab switch puts the armed tool down; doors are labelled on the DM canvas

Status: accepted. Amends ADR 0020 (its "Switching tabs never disarms a tool" decision is reversed) and ADR 0024 (the DM's picture of a door gains a label). Requested by the people playing with it, after the v2 build.

## Context
ADR 0020 kept a canvas tool armed across tab switches, so a DM could visit Tokens and come back to a ready brush, with the toolbar chip as the safety net. In play the opposite surprise turned out to be the common one: a fog brush, a fill or the door tool left armed on another tab turned the next click on the map — meant to select or move a token, or just to pan — into paint or a stray door. The chip did not prevent that; players asked for tools to drop when they change tabs.

The Walls tab lists doors as "Door 1", "Door 2", … and centres the canvas on a door when its name is clicked, but nothing on the map itself said which door was which, so a DM with several doors had to click through the list to find one.

## Decision
- **Choosing a tab puts down any armed tool that belongs to another tab.** `dm/toolStatus.ts` names each tool's owning tab once (`TOOL_TABS`: align → Maps, fog → Fog, draw and note → Draw, wall/door → Walls; `describeTool` reads it for the chip), and the pure `toolAfterTabChange(tool, tab)` keeps the tool on its own tab and returns `"none"` on any other. `DmView` applies it to every tab the DM *chooses* — a tab click or arrow key in the strip, a digit key, the calibration chip — and also drops a selected wall or door when leaving Walls (its end handles would otherwise stay live on the canvas). A tool key (`B`, `D`, `G`, …) is not a tab choice: it arms its tool and opens that tool's own tab, so it never disarms itself. The tool's *settings* (mode, brush size, snapping) still live in `DmView` and survive the switch, so re-arming is one click or key. The chip stays: it is still how a folded sidebar shows what is armed, and its name still re-opens (and expands) the owning tab. Rejected: keeping ADR 0020's rule with a louder chip — the failure was a click that did something unexpected, not a tool nobody could find.
- **Every door carries a label on the DM canvas: `D1`, `D2`, …** numbered in the Walls panel's door order, so "D2" on the map is "Door 2" in the list. `dm/WallLayer.tsx` draws them as small door-coloured tags (`door-label`), a fixed screen size at every zoom, set `DOOR_LABEL_OFFSET_PX` screen pixels off the doorway's middle along its normal (above a horizontal door, left of a vertical one, whichever way it was drawn — `doorLabelPosition`), drawn after every segment and non-listening so a click still reaches the door or the tool beneath. They follow a dragged end live and renumber when a door is added or removed. Like the walls (ADR 0024) they are DM chrome in the controls layer: the player never sees them. `DmCanvas` reports the labels as `data-door-labels` (`"D1,D2"`). Rejected: per-door names typed by the DM — a schema change, a migration and an editor for a need the numbers already meet; it can come later on top of this. Rejected: a show/hide switch — the tags are small and DM-only.

## Consequences
- No store, schema or protocol change; the player is untouched.
- Tests that relied on a tool outliving a tab trip were rewritten to the new rule (`dm/DmView.test.tsx`, `dm/FogPanel.test.tsx`, `dm/WallsPanel.test.tsx`, `e2e/sidebar.spec.ts`, `e2e/fog.spec.ts`), and the user guide no longer promises that a tool stays armed on other tabs.
