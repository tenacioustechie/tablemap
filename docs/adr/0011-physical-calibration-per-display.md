# ADR 0011: Physical calibration per display — `presentation` message, display in `hello`

Status: accepted (T006)

## Context
The point of the product is that a 1-inch mini fits one cell on the TV in the table. That needs CSS pixels per physical inch for the *player's* display, which nothing on the web platform reports; it has to be measured (a square on the screen against a ruler) or computed (TV diagonal + native resolution). The value belongs to the display, not to a campaign: it must survive reloads, apply to every campaign, and be found again when the player window reopens on the same TV. The player window is render-only and never touches storage; the DM window is the only one with the database. And only the player window knows which screen it is on.

## Decision
- **Calibration is a per-display setting in the DM's database**, not campaign state. `settings` rows `calibration:<displayKey>` hold `{ pxPerInch, method, updatedAt }` (`state/calibration.ts`, `persistence.ts`). `displayKey` is a heuristic identity built from what a page can read without the Window Management permission: `screen.width x height @ devicePixelRatio + availLeft,availTop` (position tells two same-sized displays apart; rearranging displays means recalibrating). The cell's physical size (1 inch or 25 mm, `cellUnit`) is a separate global setting.
- **The player reports its display in its `hello`** (`HelloMessage.display?: DisplayInfo`). The DM records it as DM-only bookkeeping in the store (`presentation.playerDisplay`) — this is the one thing a received message may write into the DM store, and it is deliberately outside `shared`. A DM hello now makes an already-open player re-announce, so a reloaded DM learns the display; the player also re-announces when its screen changes (`resize` + a 1 s poll — there is no cross-browser event for a window moving to another display, and the popup opens on the laptop before it is dragged to the TV). The DM does not re-send assets to a client id it has already served, so re-announcing is cheap.
- **A new unsequenced `presentation` message** carries what the player needs: `{ pxPerInch | null, cellUnit, overview, target }`. Sent after every snapshot and whenever the DM store's presentation changes; latest wins, like assets. Rejected alternative: putting it into `SharedState`. That would persist per campaign (wrong owner), leak into exports, and force a schema bump for data the campaign does not own. ADR 0010's "DM-only state otherwise" rule applies.
- **The player stage scale is locked**: `scale = pxPerInch * cellInches / cellSize`, so a cell is `pxPerInch * cellInches` CSS px whatever the map image's resolution; the map is centred (panning arrives with the viewport-rectangle task). Konva draws in CSS px, and so does the ruler square (a plain `div`), so the two agree at any device pixel ratio.
- **Overview is an explicit DM override**, session-only (not persisted). The player falls back to fit-to-window and shows a "not to scale" badge; the DM checkbox is labelled the same way. Uncalibrated displays also fit to the window.
- **Two derivations**, both pure and unit-tested: measured square `pxPerInch = sizePx / cellInches` (the target square always represents one cell, so measuring "25 mm" in 25 mm mode needs no extra maths for the user), and `hypot(width, height) / diagonalInches / devicePixelRatio` for the TV-size path (the DM types the *native* resolution, prefilled from the display report). Results outside 10–600 px/in are rejected as typos.
- A `CalibrationSession` (`state/calibrationSession.ts`) does the DM-side plumbing without React: loads the unit on start, loads a display's calibration whenever the reported display changes (stale loads are discarded), and writes on save/clear.

## Consequences
- Protocol version stays 1: old players ignore `presentation` (unknown type) and old DMs ignore `display` (extra fields are dropped). `MirrorState` gains `presentation`; snapshots and deltas carry it through untouched.
- The DM sends one extra message after every snapshot; tests asserting exact message sequences were updated accordingly.
- Same-sized, same-position displays cannot be told apart; the DM sees the reported size in the panel and can recalibrate.
- The DM canvas is unaffected: it keeps free pan/zoom. Later tasks (viewport rectangle, rotation) build on the locked scale rather than replacing it.
