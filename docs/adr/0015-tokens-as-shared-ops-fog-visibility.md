# ADR 0015: Tokens as shared ops; player visibility derived from the local fog mask

Status: accepted (T010)

## Context
The spec wants coloured-disc or image tokens with a letter/number badge, 1×1 to 4×4 cells, a grid-snap toggle, DM drag, a per-token hidden flag, and the rule that a token under fog never renders on the player view. The `Token` shape has existed in the data model since T003 (`MapScene.tokens`, validated by `isToken`, persisted and synced with the scene, copied by `duplicateMapScene`, its image asset listed by `sceneAssetIds`), so the document format does not change. What T010 decides is how tokens change, and how each window decides what the players may see.

## Decision
- **Three shared ops, no schema bump.** `map/token-add { id, token }`, `map/token-update { id, tokenId, patch }` (a `TokenPatch` = any subset of the token's fields but its id, validated field by field by `isTokenPatch`) and `map/token-remove { id, tokenId }`. The reducer is dumb: it appends, patches (same object when nothing changes) and filters. Every rule that involves geometry — snapping, clamping, default placement — lives in the DM's `tokenActions`, which dispatches the final coordinates. The player therefore needs nothing but the reducer, and the autosaved document is exactly the mirrored state. `SCHEMA_VERSION` stays 6: ops are not stored, and the token shape is unchanged.
- **Snap is "top-left on the nearest grid corner".** A token's footprint is a whole number of cells, so snapping its top-left aligns every edge with a grid line for every size; equivalently the token's centre lands on the nearest grid intersection (even sizes) or cell centre (odd sizes). Before snapping, a drag is clamped so the token's centre stays on the map (it may hang over the edge; the same rule as the player-viewport rectangle). Snapping is applied live during a drag (the node jumps cell to cell) and once more on release; the release dispatches one `map/token-update`.
- **Player visibility is derived, not synced.** A token is drawn on the player when it is not flagged hidden *and every cell of its footprint is revealed*, the fog being sampled at the centre of each cell (`state/tokens.ts: tokenVisibility`; cells off the map count as fogged). Each window evaluates this against its own fog mask: the fog mask is already derived identically in both windows from the op log (ADR 0012), so no "visible to players" flag travels and nothing can get out of step. The DM draws every token; fogged ones are simply under the half-opaque fog layer (the "dimmed context" the spec wants) with a faint dashed box, hidden ones at reduced opacity with a dashed ring.
- **"Every cell" rather than "any cell" or "the centre".** A large monster half inside the revealed room would leak its position if any revealed cell sufficed; sampling only the centre would show a 4×4 token whose centre cell happens to be revealed. Hiding until the whole footprint is revealed never shows anything the fog would hide. Feathered edges are read at 50 % (the same threshold the bitmap raster uses), so a token whose cell centre is in the soft edge flips exactly where the fog is half transparent.
- **The fog is sampled from the rendered mask canvas through a 1×1 scratch canvas.** `createFogSampler` copies one pixel with `drawImage` into a scratch canvas created with `willReadFrequently` and reads that. The big mask canvas never sees `getImageData`, so browsers keep it on their accelerated path for painting (a `getImageData` on it would both stall the GPU pipeline per sample and, after a few reads, push Chrome into software rendering for every subsequent fog op). The stage recomputes visibility when the mask updates (`useFogMask` exposes a `version` and a fresh `isFogged` function per update), when the tokens change and when the grid changes. While the mask is `waiting` (a base PNG this window lacks) every pixel is fogged, matching what is drawn.
- **Token images are `token-image` assets.** Stored by `tokenActions.addImage` with the same validation as map import, pushed to the player by the existing asset path (ADR 0008; `sceneAssetIds` already listed them), deleted once nothing references them (a duplicated map shares them). The DM reads the active map's token images from the database (`useAssetBlobs`), the player from its mirror. Until the Blob has arrived a grey disc with the badge stands in.
- **Selection is DM UI state.** `DmView` holds the selected token id (reset on a map switch, self-clearing when the token is gone); the panel edits the selected token through `TokenActions`; the canvas selects on click. Tokens are interactive only while no canvas tool runs, so the fog and alignment tools get every press.

## Alternatives considered
- **A synced "visible" flag computed by the DM.** Rejected: the DM would have to recompute it after every fog op and every move and send extra deltas, and a player with a different mask state (e.g. `waiting` for a base) could show a token on black.
- **A second (bitmap) fog raster per stage for queries.** Rejected: doubles the rasterisation work and memory (8 MB for a 4k map) and needs a full readback of the base PNG on compaction, for a handful of pixel reads per fog op.
- **Visibility by the token's centre only, or by any revealed cell.** Rejected as above.
- **A placement tool on the canvas.** Rejected for now: "Add token" drops the token in the middle of what the TV shows and the DM drags it from there; a click-to-place tool can come with annotations.
- **Model field rename to `hiddenFromPlayers`.** The task uses that name; the existing model field is `hidden` with the same meaning and is already persisted. Kept as is.

## Consequences
- The stage has one more layer (the tokens' canvas, between grid and fog), so every stage now has one more `<canvas>`; tests counting canvases were updated. An empty layer costs one transparent canvas.
- Token drags are pointer-rate Konva node moves; only the release dispatches, so autosave and the delta path see one op per move.
- Visibility is recomputed on every mask update with `size²` pixel reads per token (at most 16), each a 1×1 `drawImage` + `getImageData` on the scratch canvas.
- The player view exposes `data-tokens`, `data-tokens-shown`, `data-tokens-fogged`, `data-tokens-hidden` on its stage for tests; the DM canvas exposes `data-token-tool` and the stage `data-token-selected`.
