# ADR 0016: Annotations as shared ops with DM-only entries stripped from the wire; pings as unsequenced events

Status: accepted (T011)

## Context
The spec wants DM-only pinned notes (a marker with popover text that must never reach the player render), a ping (an animated pulse on the player view where the DM alt-clicks) and a freehand draw layer whose strokes are visible to the DM only or to both views, with a colour picker, an eraser and clear-layer. The `Annotation` shape (note | drawing, with a per-drawing `visibility`) has existed in the data model since T003 (`MapScene.annotations`, validated by `isAnnotation`, persisted with the scene). Two tensions decide the design:

- Notes must be **persisted** (they belong to the map and the campaign document *is* the `SharedState`), yet `shared.ts` promises that DM-only data never goes to the player. Keeping notes in the document and merely not drawing them on the player would still ship their text to the player window on every snapshot.
- A ping is an **event**, not state: it plays for two seconds and is gone. Putting it in the sequenced state would persist it, replay it to late players and cost an undo-visible op.

## Decision
- **Three shared ops, no schema bump.** `map/annotation-set { id, annotation }` (upsert: replaces by id in place, else appends; same state when unchanged), `map/annotation-remove { id, annotationId }` and `map/annotations-clear { id, annotationKind }`. The reducer is dumb; geometry (the eraser's hit test) lives in the DM's `annotationActions`. `SCHEMA_VERSION` stays 6: the annotation shape is unchanged and every existing document already validates.
- **One visibility rule, in one place.** `state/annotations.ts: isAnnotationVisibleIn(annotation, view)`: the DM sees everything; the player sees a drawing only with `visibility: "all"` and never sees a note — decided by the *kind*, so a malformed `visibility` on a note cannot leak it. Every renderer asks this function.
- **DM-only annotations never leave the DM window.** The DM's publisher runs every snapshot through `sharedStateForPlayer` (each map's annotations filtered) and every delta through `opsForPlayer`: `campaign/replace` and `map/add` are filtered the same way, and a `map/annotation-set` of a DM-only annotation is rewritten into a `map/annotation-remove` of that id — harmless if the player never had it, correct if the annotation just stopped being shared. The seq still advances by one per dispatch, so the player stays contiguous; a dispatch that only touched notes becomes a delta of no-op removals. The player's mirror therefore never holds a note or a DM-only drawing, its stage additionally filters by the same rule (defence in depth), and the note *marker* is DM chrome drawn by the DM canvas in its controls layer, not by the shared stage — there is no code path in `src/player/**` or `src/map/**` that draws a note (guarded by `boundary.test.ts`). The DM's own store (and so the autosaved document) keeps everything.
- **Drawings sit under the fog, pings above it.** The annotation layer is between the tokens and the fog, so a shared stroke in a fogged area is as hidden as the map under it. A ping is a "look here" and reveals nothing, so it is drawn above the fog. Both are non-listening layers of the shared stage; the ping layer only exists while a pulse plays.
- **Pings are a `ping` sync message.** Unsequenced like `presentation` and `asset`, never in a snapshot (a late player has no use for old pings), carrying `{ id, mapId, x, y, at }` with the DM's `Date.now()`. The DM store's `sendPing` records it locally (a DM-only, unsequenced `pings` list, for the DM canvas's own pulse) and notifies `onPing` listeners; the sync layer posts it. Both windows bound their list without a clock: `addPing` drops pings that had already expired *at the new ping's timestamp* and caps the list at 16; views draw `activePings(pings, now)` and derive the animation from `pingProgress`, driven by one `requestAnimationFrame` clock that runs only while a pulse is playing. The two windows share a machine (ADR 0003), so the DM's timestamps are comparable with the player's clock.
- **Alt-click is the ping gesture, whatever tool runs.** The stage reports an Alt press as `onAltClick` and keeps that press from the pointer tool, so the DM can ping mid-fog-painting without switching tools.
- **The pen reuses the fog brush gesture.** `map/fogGesture.ts` with the brush tool yields exactly what a stroke needs (a thinned drag path); the DM canvas turns it into a drawing with the current colour, width (map pixels, so it zooms with the map) and visibility. The eraser removes whole strokes within reach (screen-constant radius) on every press and drag move; there is no per-segment splitting.
- **Notes are placed by a click and edited in a DOM popover** at the marker's screen position; the marker is draggable. Which note is open is DM UI state in `DmView` (reset on a map switch).

## Alternatives considered
- **A separate DM-only store slice for notes, persisted outside the campaign document.** Rejected: notes belong to the map and must travel with an exported campaign (T012); a second document would have to be kept in step with map ids, duplication and deletion.
- **Rendering-only filtering (notes travel, the player just does not draw them).** Rejected: the text would still be in the player window's memory and on the BroadcastChannel; "invisible under all conditions" is easier to guarantee when it never arrives.
- **Pings as ops (`map/ping`) or as presentation state.** Rejected: an op is persisted, sequenced and replayed; presentation is "latest wins" state, so two quick pings would collapse into one and a ping would have to be explicitly cleared.
- **Per-drawing visibility editing / moving strokes.** Not needed by the spec; a stroke is created with the tool's visibility and removed by the eraser or clear. The upsert op leaves the door open.

## Consequences
- The stage has one more permanent layer (annotations) and a transient one (pings), so every stage has one more `<canvas>`; tests counting canvases were updated.
- The DM's publisher does a shallow filter of the shared state per snapshot and per delta (a map is copied only when it has DM-only annotations); the mirrored state can legitimately differ from the DM's, which the stage's `data-annotations` attribute reflects per window.
- A new module `state/annotationActions.ts` is DM-only (ESLint `no-restricted-imports` + `boundary.test.ts`), and `boundary.test.ts` also asserts that no `src/player/**` source mentions notes or sends pings.
- A ping costs one BroadcastChannel message and two seconds of animation frames on each window; nothing is stored.
