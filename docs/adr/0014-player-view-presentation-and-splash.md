# ADR 0014: Player view control — pan centre, rotation, blackout and splash in the `presentation` message; the splash image as campaign state (schema v6)

Status: accepted (T009)
Amended by ADR 0018: the viewport rectangle's drag handle moved to an underlay beneath the tokens (the visible frame stays in the controls layer), so a drag starting on a token moves the token.
Amended by ADR 0019: with no splash image chosen the splash shows the bundled default artwork; the title card is an explicit choice (`SharedState.splashTitleCard`, schema v7).
Amended by ADR 0023 (T019): the rotation is no longer forgotten on reload — it is remembered per display in settings (`rotation:<displayKey>`) and reapplied when the player window reports that display; the pan centre and the splash-on-switch preference are still session-only.

## Context
T006 (ADR 0011) locked the player stage scale to the display's calibration and centred the map. T009 adds the rest of the spec's "player view control" and "table tools": the DM pans the player view by dragging a rectangle on the DM canvas, rotates it in 90-degree steps (the TV is in the middle of the table; players sit on every side), blacks the TV out instantly, and shows a splash screen — the campaign's title card or a chosen image — between scenes or on demand. Pan must feel live (the TV follows the drag), rotation must not disturb the calibration, and blackout/splash must override every layer at once. The player window stays render-only.

## Decision
- **Pan, rotation, blackout and splash are presentation, not campaign state.** `PlayerPresentation` (the unsequenced `presentation` message of ADR 0011) gains `center: { x, y } | null` (the map point at the middle of the player display, in map pixels; null = the map's centre), `rotation: 0 | 90 | 180 | 270`, `blackout` and `splash`. They describe how the DM is presenting the table right now, like `overview`: they belong to the session and the display, not to the document, so they are never persisted nor exported, and they need no schema change. "Latest wins" is exactly right for a drag: dozens of centre updates a second, no sequencing, a dropped intermediate is harmless. Rejected: a `map/set-view` shared op per drag move (would bump `seq`, hit autosave and the delta path at pointer rate, and put a transient view into the campaign document).
- **The centre belongs to the active map.** The DM store applies `presentationForMapSwitch` in the same commit as any dispatch that changes `activeMapId` (scene switch, removal of the shown map, opening a campaign): the centre is dropped (a different map has a different middle) and, with the DM-only `splashOnSwitch` preference on, the splash is raised. Doing it in the store rather than in a React effect keeps the reset atomic with the op and makes it unit-testable; the delta and the presentation message go out back to back.
- **One pure module for both directions.** `map/playerView.ts` turns a presentation + scene + display size into a `PlayerView` (`center`, `scale`, `rotation`), and from it derives the player's stage transform (`display / 2 − rotate(center × scale)`) and the DM's viewport rectangle (`display / scale` in map pixels, width and height swapped by a quarter turn, centred on the centre). The two are inverses and are tested against each other for every rotation. The rectangle is drawn on the DM canvas in a listening Konva layer; dragging it writes the centre. Its size comes from the display the player window reported in its `hello` (assumed full-screen; 1920×1080 until one has connected). The player scale is only "locked" (and pan honoured) while calibrated and not in overview; a fitted map is fitted to the *rotated* display and centred — there is nothing to pan.
- **Rotation is a stage transform, applied after the scale.** Konva's node order is translate → rotate → scale, so `Viewport` gained an optional `rotation` and `screenToMap` / `mapToScreen` honour it. The scale is untouched by rotation, which is what "rotation preserves calibration scale" means: a calibrated cell is the same number of screen pixels at any quarter turn (checked in unit tests and in e2e). Titles and the splash are DOM, rotated with CSS so they read the right way up for the players. Rejected: rotating the map image itself (would break every map-pixel coordinate the fog and, later, tokens use).
- **Blackout and splash are DOM overlays over the stage, not stage state.** An opaque black `div` (blackout) and a black `div` with the image or the title (splash) sit above the Konva canvases. They appear the instant the message is applied, cost nothing to lift, and leave the stage mounted underneath with its fog mask intact, so ending a blackout is as instant as starting one. Priority: blackout > ruler screen > splash > scene. Rejected: unmounting the stage (a rebuild of a 4k fog mask on the way back) or painting a black Konva layer (a redraw of the whole stage for a solid colour).
- **The splash image is campaign state — schema v6.** The chosen image is a `splash-image` asset referenced by `SharedState.splashImageAssetId` (null = title card), chosen through `campaign/set-splash-image` and stored/deleted by `state/splashActions.ts` with the same asset bookkeeping as map images. It is content the DM prepared for the campaign, so it is autosaved and will travel in exports; `migrateCampaign` v5 → v6 adds the null field. The player receives it like any asset (right after the active map's, so it is ready when the splash goes up) and shows the title until it lands.
- **Splash on scene switch is an opt-in preference with manual dismissal.** A timed splash was rejected: a DM switches scenes precisely to set up behind the splash (pan the rectangle, reveal the first rooms), which takes an unknowable time, and a timer would make every existing "the player shows the new map" behaviour asynchronous. The preference lives in the DM-only presentation slice and is off by default, so scene switches stay instant unless the DM asks.

## Consequences
- Protocol version stays 1. `isPlayerPresentation` is strict: a player of an older build rejects the richer message as `invalid-shape` and keeps its defaults (both windows are always served from the same build, so this only matters for a stale tab).
- v5 builds refuse v6 documents as `newer-schema`; v5 documents load with a null splash image.
- The DM canvas gained a fourth canvas (the controls layer). The rectangle has no fill so the DM's own pixels — which e2e tests sample — are untouched; Konva hit-tests the interior regardless.
- Rotation, the pan centre and the preference are forgotten on reload. Per-display rotation in settings (next to the calibration) is the obvious follow-up if a permanently rotated TV proves annoying.
- Pan is not meaningful for uncalibrated displays; the panel says so, and the rectangle is inert there.
