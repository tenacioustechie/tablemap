# ADR 0020: Tabbed DM sidebar and a tool status chip in the toolbar

Status: accepted (T016). Amended by ADR 0022 (T018: the chip also shows the key that arms the tool, and the tabs answer to `1`–`5`). Amended by ADR 0023 (T019: the sidebar is 300 px and collapsible from the tab strip, remembered under `tablemap.dm.sidebar`; the blank-map form folds behind a disclosure; the toolbar also shows the active map's name and a calibration chip). Amended by ADR 0024 (T101: a sixth tab, **Walls**, after Draw; Table answers to `6`). Amended by ADR 0027 (T110: a seventh tab, **Turns**, after Tokens, answering to `7`).

## Context
The DM view was one 260 px sidebar stacking every section top to bottom: campaign name, maps, grid, fog of war, tokens, annotations, calibration, player view. It worked, but during a session the three panels a DM touches every minute (fog, tokens, notes) sat below the map list and the import / blank-map forms and above the once-per-evening calibration and splash settings, so a laptop screen scrolled two or three times over. Worse, an armed fog brush stayed armed after its panel scrolled out of view, with the cursor as the only cue. `docs/plans/2026-09-dm-usability.md` §1–§2 has the review.

## Decision
- **Five tabs grouped by phase of use, not by feature.** Maps (campaign name, map list, import, blank map, grid — prep), Fog, Tokens, Draw (play), Table (calibration, player view — setup). `dm/SidebarTabs.tsx` implements the WAI-ARIA tabs pattern (`tablist` / `tab` / `tabpanel`, `aria-selected`, `aria-controls`, roving `tabIndex`, arrow keys select as they move). Rejected: a floating tool palette over the canvas (more clicks on the canvas, blurs the render-only boundary of the stage) and an auto-hiding "play mode" (a second UI mode to explain; T019's collapse button plus T018's shortcuts get the benefit).
- **Inactive tab panels are unmounted, not hidden.** One panel in the DOM keeps the tree small and makes "which controls are reachable" a question with one answer per tab. The cost is that a panel's transient drafts (a rename box, the blank-map fields, the TV-size fields) reset on a switch; every setting that matters — tool settings, the token selection, the open note — already lives in `DmView` or the store and survives. Tests that drive a panel through `DmView` open its tab first (`src/test/dmTabs.ts`, `e2e/helpers.ts`).
- **The chosen tab is remembered in `localStorage` (`tablemap.dm.tab`), default Maps.** It is DM-window UI state like nothing else in the app: not campaign content (it must not travel in exports or over the channel), not per-display (calibration's storage), and not worth a schema field. A fresh browser opens on Maps because a new campaign has nothing to fog yet. The read and the write are guarded: a disabled or full storage costs the memory, never the switch.
- **Switching tabs never disarms a tool.** The armed tool is `DmView` state and the canvas runs it; the tabs are pure presentation over the panels. A DM opens Tokens to tweak a badge and comes back to a brush that is still ready. What makes that safe is the **tool status chip** in the toolbar (`data-testid="tool-status"`): visible only while a tool is armed, naming the tool and its mode from the pure `describeTool` in `dm/toolStatus.ts` ("Fog · reveal brush", "Draw · eraser", …), with **Stop (Esc)** and a click on the name that opens the owning tab. Rejected: disarming on a tab switch (turns every tab visit into Esc + re-arm, which is the scrolling problem in another form) and showing the armed tool only inside its panel (invisible from any other tab — the very failure the tabs would otherwise make worse).
- **Blackout, splash, the player-window controls and the status stay in the toolbar.** They are the one-click session controls that must be reachable whatever tab is open; putting blackout on the Table tab would mean two clicks to blank the TV in an emergency. The toolbar wraps onto a second line when the chip does not fit.

## Consequences
- No store or protocol change; the player is untouched. `DmTool` moved to `dm/toolStatus.ts` (re-exported from `DmView`) so the chip's labels are testable without React.
- Every e2e spec and every `DmView`-driven unit test that reaches a panel control opens the tab first; that is a mechanical `openTab` call, not a weakened assertion. The 768 px-tall window criterion is checked in `e2e/sidebar.spec.ts` on the Fog tab with a tool armed (the tallest state of the busiest panel).
- T018's keyboard shortcuts will name the tabs (`1`–`5`) and add the shortcut hints to the chip; T019's sidebar collapse button lives in the same tab strip.
