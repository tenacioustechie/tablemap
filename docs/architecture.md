# Architecture

Local-first TypeScript SPA. No backend. Ships as static files; runs offline once loaded.

## Windows & sync
- Routes: / campaign manager, /dm DM view, /player player view. Hash router (`createHashRouter`) so static hosting and file:// URLs work. Route table lives in `app/src/routes.tsx`; path constants in `app/src/routePaths.ts` (dependency-free so any module can import them). `/dm` mounts `dm/DmRoute.tsx`, which opens a campaign from storage (load-on-start) before rendering `DmView` and runs autosave while mounted; `/` mounts `CampaignManager.tsx` (list, create, open, rename, delete, **Export** per campaign and an **Import campaign (.zip)** picker — T012; the archive is handed to an injectable `saveFile`, by default `download.ts: downloadBlob`, an object URL on a clicked link; outcomes show in a `campaign-manager-notice` line, failures in the error banner).
- DM view opens /player with window.open (named window `tablemap-player`, `popup` feature for a chrome-less window). The DM window retains the handle in a controller (`app/src/dm/playerWindow.ts`, pure logic with injectable deps; React binding `usePlayerWindow.ts`) and uses it to focus, full-screen and close the player window. Re-clicking "Open" focuses the existing window instead of spawning another. The hook polls the handle (500 ms) for closed/fullscreen changes because no cross-window event survives the popup's own navigation.
- Fullscreen: the DM toggle calls `requestFullscreen` on the player document via the handle. Browsers only honour that from a user gesture in the *target* window, so the request is often denied (it is in headless Chromium). The DM view then shows a hint, and the player view offers an in-window fallback: press **F** or double-click. See ADR 0005. The OS puts the window on the TV (Window Management API where available, manual drag as fallback).
- Player/DM boundary: `src/player/**` must never import from `src/dm/`. Enforced by an ESLint `no-restricted-imports` rule scoped to `src/player` and by a unit test (`src/player/boundary.test.ts`).
- DM layout (`DmView`, T016, ADR 0020): top toolbar (player-window controls, then the **Blackout** and **Show splash** switches — `blackout-toggle` / `splash-toggle`, `aria-pressed` — then (T019, ADR 0023) the **active map's name** (`active-map-name`, `data-map-id`; "No map shown" without one) and the **calibration chip** (`calibration-chip`, `data-calibrated`; text from the pure `describeCalibration(calibration, cellUnit)` in `dm/toolStatus.ts` — `"1 inch = 96 px/in"`, one decimal at most, or `"Not calibrated"`; a click opens the Table tab), then the **tool status chip** and the player-window status), left sidebar (300 px, `SIDEBAR_WIDTH`, collapsible — below) with **six tabs**, main canvas area (`dm/DmCanvas.tsx`, the Konva stage for the active map with wheel zoom / drag pan, a **Fit** button, the player viewport rectangle, the note markers and the walls). The sidebar is `dm/SidebarTabs.tsx`: a WAI-ARIA tab strip (`role="tablist"` / `role="tab"` with `aria-selected` + `aria-controls`, roving `tabIndex`, Left / Right / Home / End move and select; `data-testid="dm-tab-<id>"`) over one `role="tabpanel"` (`data-testid="dm-tabpanel"`, `data-tab="<id>"`). The strip also holds the **collapse toggle** (`sidebar-toggle`, `aria-expanded`; T019): collapsed, the sidebar is a 44 px strip (`SIDEBAR_COLLAPSED_WIDTH`) of tab initials (each tab keeps its `aria-label`; the tablist is `aria-orientation="vertical"`) and **no tabpanel is mounted**; choosing a tab (click or arrow key) expands it, as do the tab keys `1`–`6` and both toolbar chips (`DmView`'s `selectTab`), whereas a tool key only records the tab. The root grid's first column and the `aside`'s width follow the state (`data-sidebar` on `dm-view`, `data-collapsed` on `dm-sidebar`) and the canvas remeasures through `map/useContainerSize.ts`. Tabs, in order, and what `DmView` mounts in each — **only the active tab's panels are in the DOM**: **Maps** (campaign name, `dm/MapPanel.tsx`, `dm/GridPanel.tsx`), **Fog** (`dm/FogPanel.tsx`), **Tokens** (`dm/TokenPanel.tsx`), **Draw** (`dm/AnnotationPanel.tsx`), **Walls** (`dm/WallsPanel.tsx` — T101 / T102, ADR 0024 / ADR 0025: the **Wall** and **Door** tool buttons (`wall-tool-wall` / `wall-tool-door`, `aria-pressed`; a click arms the tool with that kind, a second click on the armed kind disarms it; `wall-stop` while armed), the **Snap to grid** checkbox (`wall-snap`; on by default), the active map's wall and door counts (`wall-count`, `wall-summary` with `data-walls` / `data-doors`), the **Doors** list (T103: `door-list` with `data-doors-open`, one `door-item` per door in document order with `data-door-id` / `data-open` / `data-selected`, its label button `door-select` — "Door n · open" / "Door n · closed" from the pure `describeDoor(n, open)` — selecting the door and centring the canvas on it, and `door-toggle` (**Open** / **Close**, `aria-pressed`) toggling it), what is selected (a wall clicked on the canvas or a door picked from the list: `wall-selected` with `data-wall-id` / `data-wall-kind`; `wall-selected-kind` "wall" / "door (closed)" / "door (open)" and `wall-selected-length` in grid cells to one decimal, from the pure `describeWallKind` / `describeWallLength`; **Delete (Del)** `wall-delete`) or a hint (`wall-selection-hint`), and **Clear walls** (`walls-clear`, disabled when there are none) behind an inline confirm (**Confirm clear walls** `walls-clear-confirm` dispatches one `map/walls-clear`; `walls-clear-cancel`; a pending confirm folds away on a map switch or when the walls change). The tool settings are the DM-only `WallToolSettings` in `dm/wallTool.ts` (`tool` wall | door, `snap`; `WALL_SNAP_PX` 12, `WALL_CLICK_THRESHOLD_PX` 6), held by `DmView` like the fog settings; the selection is `DmView` UI state like a token's (reset on a map switch, cleared when the segment goes or any tool is armed); **Delete** / **Backspace** outside a text field remove the selected segment (`map/wall-remove`), Esc with no tool armed deselects. Every wall edit is one shared op straight from `DmView` (`map/wall-set` with a `createWall` / `createDoor` of a fresh `nanoid` for a drawn segment, `patchWall` for a moved end; a door toggle, from the canvas or the list, is one `map/door-set-open` of the door's opposite state through `DmView`'s `toggleDoor`) and none is undoable), **Table** (`dm/CalibrationPanel.tsx`, `dm/PlayerViewPanel.tsx`). The active tab is DM-window UI state, not store state: `useRememberedTab(storage)` keeps it in React state and mirrors it to `localStorage` under `tablemap.dm.tab` (default Maps; an invalid or unreadable value falls back to Maps; a throwing storage is tolerated); `DmView` takes an injectable `tabStorage` for tests. `useRememberedSidebar(storage)` does the same for the collapsed state under `tablemap.dm.sidebar` (`collapsed` | `expanded`; anything else, or no storage, means expanded). Every tool setting, the token selection and the open note live in `DmView` or the store, so **switching tabs never disarms or changes a tool**; only transient form drafts inside a panel (rename box, blank-map fields, TV-size fields) reset when their panel unmounts. The blank-map form is behind a **New blank map** disclosure in `dm/MapPanel.tsx` (`blank-map-disclosure`, `aria-expanded`, closed by default; the import picker stays visible — T019). Canvas tools are mutually exclusive: `DmView` holds one `DmTool` (`none` | `align` | `fog` | `draw` | `note` | `wall`, declared in `dm/toolStatus.ts`), reset whenever the active map changes; tokens are draggable, and walls selectable, only while it is `none`. While a tool is armed the toolbar shows the chip (`tool-status`, `data-tool`, `data-tab`): the tool's name and mode from the pure `describeTool(tool, fogSettings, drawSettings, wallSettings) → { label, tab, key } | null` (`"Align grid"` → Maps; `"Fog · <reveal|hide> <brush|rectangle|lasso>"` → Fog; `"Draw · pen"` / `"Draw · eraser"` and `"Place note"` → Draw; `"Walls · wall"` / `"Walls · door"` → Walls), as a button (`tool-status-name`) that opens the owning tab, plus **Stop (Esc)** (`tool-stop`), which sets the tool to `none` exactly as Esc does outside a gesture. An Alt-click is a ping under any tool (T011). The whole DM view is a drop target for image files (`data-dragging` + an overlay while a file is over it); the file picker lives in the map panel. Import UI state (queue, "Importing…", last error) is `dm/useMapImport.ts`.
- Keyboard shortcuts and the cheat sheet (T018, ADR 0022): the keymap is the pure `dm/shortcuts.ts` — `SHORTCUTS` (the ordered table: `{ key, label, group, command }`; tabs `1`–`6` in `DM_TABS` order (`5` Walls, `6` Table since T101), `?` help, `V` stop, `G` align, `N` note, fog `R` / `H` mode, `B` / `X` / `L` tool, `[` / `]` brush radius ∓ `FOG_BRUSH_RADIUS.step` (8 px, clamped by `fogTool.ts: stepBrushRadius`), draw `P` pen / `E` eraser, walls `W` wall / `D` door — T102), `MOUSE_GESTURES` (wheel, drag, Space / middle drag, Alt-click, a click on a wall with no tool armed, a click on a door (T103), Esc, undo / redo — the cheat sheet's second column), `shortcutFor(event) → ShortcutCommand | null` (null with Ctrl / Cmd / Alt, with Shift except for `?`, or when `isEditableTarget(event.target)` — input, textarea, select, contenteditable — which `DmView`'s undo / redo listener and the canvas's Space watcher share), and `shortcutKeyFor(command)` (the chip's key). `DmView` listens on the window and runs the command: tab → `setTab`; stop → tool `none`; brush-radius → the fog settings only (no arming, no tab switch); the tool commands need an active map like the buttons and *arm* — never toggle — the tool (`fog-mode` / `fog-tool` set that setting and the tool to `fog`, `draw-mode` to `draw`, `wall-tool` to `wall`, `note`, `align`), then open the owning tab. Esc, Space and the modifier chords are not commands. The `?` key and the toolbar's **?** button (`shortcut-help-button`, `aria-pressed`) toggle `dm/ShortcutHelp.tsx`: a modal (`shortcut-help`, `role="dialog"`, focused on open; `shortcut-help-backdrop` closes on a click; `shortcut-help-close`) rendering `SHORTCUTS` by group (`shortcut-row` with `data-key` + `shortcut-label`) and `MOUSE_GESTURES` (`gesture-row` + `gesture-label`), so it cannot drift from the keymap. While it is open other shortcuts are ignored and **Esc closes only the sheet**: `DmView` registers a capture-phase keydown listener on the document that closes it and stops the event before the tools' own Esc listeners on the window see it. The chip shows the armed tool's key (`tool-status-key`, from `describeTool(...).key` = `shortcutKeyFor` of the command that arms that very tool: `G`, `B` / `X` / `L`, `P` / `E`, `N`, `W` / `D`).
- Pan override (T018, ADR 0022): the DM can pan whatever tool is armed — a **middle-button drag**, or a drag while **Space** is held. `MapStage` does the panning itself (`panOverride` prop; the middle button, `PAN_MOUSE_BUTTON`, needs no prop): the press records the pointer and the viewport, window `mousemove` / `mouseup` listeners report `start + offset` through `onViewportChange` (so the pan survives leaving the stage) and the tool's `onDown` / `onMove` / `onUp` are not called until the release; Konva's own drag-pan is off while `panOverride` is set so a left press cannot start both; `data-panning` reports it; the middle press is `preventDefault`ed against the browser's autoscroll; the player (`interactive` false) is unaffected. `DmCanvas` watches Space on the window (not from an editable target; released on window `blur`), sets `panOverride`, shows the `grab` cursor, reports `data-pan-override` (`space` | `none`), and while Space is down withholds the token tool, the player-viewport handle and the note markers' draggability so the pan wins over them too. Space's default (a focused sidebar button would click on release) is suppressed only while the pointer is over the canvas (`mouseenter` / `mouseleave` on the surface); over the sidebar the key keeps activating what is focused.
- Grid tools (T005): `GridPanel` edits the active map's cell size, offset and the per-view style (show / colour / opacity for the DM view and the player view separately) through `MapActions.setGrid`, and toggles the **alignment tool**. `DmView` owns the "aligning" flag (reset whenever the active map changes) and passes `DmCanvas` an `alignment` prop (`onAligned(geometry)`, `onCancel`). While aligning, the canvas hands the stage a `pointerTool` instead of drag-pan, feeds the pure state machine in `map/alignment.ts` with pointer events in map pixels, draws the preview box as a stage `overlay`, shows a hint (`data-testid="align-hint"`, plus `align-error` when the box is too small), and listens for Esc. A completed alignment becomes one `map/set-grid` op with the derived `cellSize`/`offsetX`/`offsetY` and the styles untouched.
- Map rotation (T017, ADR 0021): the Grid section of `GridPanel` also holds **Map rotation** — **⟲ 90°** / **⟳ 90°** (`map-rotate-ccw` / `map-rotate-cw`, aria-labels "Rotate map counter-clockwise" / "Rotate map clockwise", distinct from the Table tab's "Rotate player view …") around the current value (`map-rotation-value`). A click calls `DmView`'s `rotateMap`, which puts any armed tool down (its gesture would be in the old coordinates) and runs `MapActions.rotate(activeMapId, 270 | 90)`; the panel disables both buttons until the promise settles (a base fog mask may be being baked). The turn is a document change to that map — picture, grid, fog, tokens and annotations together, on both windows — as opposed to the player view's rotation, which turns the TV's presentation of every map. `DmCanvas` refits on the size change and reports `data-map-size` / `data-map-rotation` on its surface.
- Fog of war (T007 + T008, ADR 0012, ADR 0013): `FogPanel` edits the DM-only `FogToolSettings` (`dm/fogTool.ts`: `mode` reveal | hide, `tool` brush | rect | lasso, brush `radius` in map px (slider 4–400, default 40), `feather` on by default, `snap` off by default) that `DmView` holds in state, turns the `fog` tool on with **Brush** / **Rectangle** / **Lasso** (clicking the active one, **Stop** or Esc turns it off), offers **Undo** / **Redo** (also Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z, Ctrl/Cmd+Y from anywhere but a text field), **Hide all** / **Reveal all**, and the log length (`data-testid="fog-op-count"`; buttons are `fog-mode-*`, `fog-tool-*`, `fog-brush-radius`, `fog-feather`, `fog-snap`, `fog-undo`, `fog-redo`). With the tool on, `DmCanvas` takes a `fog` prop (`{ settings, onShape, onCancel }`) and feeds the stage's pointer events to the pure gesture machine `map/fogGesture.ts` (`reduceFogGesture`: brush → one `stroke` of the thinned drag path, `FOG_MIN_STEP_PX` = 3 screen px between kept points, a click is a one-point stroke = a dot; rect → the box, under `FOG_MIN_DRAG_PX` = 2 screen px is a click and ignored; lasso → the drag path closed into a `polygon`, needs ≥ 3 kept points and a box over the minimum). With `snap` on the shape is expanded to whole grid cells by `map/fogSnap.ts` (`snapShapeToCells` → one `rects` shape; feather is then off: cells have hard edges). The live preview is `gestureShape` put through the same snapping: a *reveal* preview is drawn inside the fog layer with `destination-out` (`MapStage`'s `fogOverlay` prop), so the DM sees the map appear under the brush as they drag without the mask being touched; a *hide* preview is a red tint in the overlay layer; the brush also shows its footprint under the pointer. The tool stays on for the next gesture; Esc abandons a gesture in progress or leaves the tool. The canvas surface reports `data-fogging` (mode or `false`), `data-fog-tool` and `data-fog-gesture` (`dragging` | `idle`). Completed shapes go to `FogActions.reveal` / `hide` with the feather width (`fogFeatherPx(cellSize)` = 30 % of a cell, 4–64 px) when feathering applies, i.e. one `map/fog-op` per gesture — a brush stroke is committed on release, not streamed per pointer move (ADR 0012's advice; keeps the log short and makes one stroke one undo step). The DM canvas reads the map's fog base PNG from the database (`useAssetBlob`) and hands it to the stage as `fogBase`. Undo / redo is `state/fogHistory.ts` (below), created by `DmView` over `FogActions.apply`. Below the fog controls the panel holds the active map's vision dim override (T105, ADR 0026): **Dim unseen areas on the TV** (`vision-dim`, a select Auto / On / Off showing `scene.visionDim`) dispatches one `map/set-vision-dim` per change straight from the panel, and `vision-dim-hint` (`data-uses-vision` = `mapUsesVision(scene)`) says what the setting resolves to on this map, from the pure `describeVisionDim(visionDim, seeing)` (`"Off: no token on this map has vision."`, `"On: 2 tokens on this map have vision."`, `"Always on for this map."`, `"Always off for this map."`). `MapStage` dims by it (T107, see Rendering).
- Calibration (T006, ADR 0011): `CalibrationPanel` shows the display the player window reported, the cell unit (1 inch / 25 mm), the **overview** override, and the two ways to calibrate: **ruler** (puts the player on a ruler screen showing a white square; ±1/±10 buttons and a size field grow/shrink it; "It measures 1 inch: save") and **TV size** (diagonal + native resolution, prefilled from the display report). Saving goes through a `CalibrationSession` (`state/calibrationSession.ts`, created by `DmView`, injectable in tests) that persists per display and updates the store's `presentation`, which the sync layer pushes to the player. Once the display is calibrated the TV-size fieldset sits behind a **Recalibrate from the TV size** disclosure (`tv-size-disclosure`, `aria-expanded`; T019); while it is uncalibrated the fieldset is open as one of the two ways in. Tests reach both folded forms through `src/test/dmPanels.ts` (`openBlankMapForm()`, `openTvSizeForm()`) and `e2e/helpers.ts` (`openBlankMapForm(page)`, `openTvSizeForm(page)`), which open the owning tab and the disclosure whatever state it is in.
- Player view control (T009, ADR 0014): `PlayerViewPanel` rotates the player view in quarter turns (**⟲ 90°** / **⟳ 90°**, `rotation-value`), recentres it (`recentre-player-view`), holds the **Show splash when switching maps** preference (`splash-on-switch`), the splash source radio **When no splash image is chosen: Default artwork / Campaign title** (`splash-source-default` / `splash-source-title`, dispatching `campaign/set-splash-title-card`; T015, ADR 0019) and the splash image picker (`splash-file-input`, `clear-splash-image` "Remove splash image", `splash-error`; through `state/splashActions.ts`). The thumbnail `splash-thumb` always shows what is in effect (`data-splash-kind` `image` | `title` | `default`): the chosen image, a title placeholder, or the bundled artwork `src/assets/splash-default.png`, which the DM panel and the player view both import by URL (`import defaultSplashUrl from "../assets/splash-default.png"`) so Vite bundles and hashes it into `dist/assets/` — it never goes through the database or the asset channel. `DmCanvas` always draws the **player viewport rectangle** in the stage's `controls` layer: the map area the player display shows, from `map/playerView.ts` (`resolvePlayerView` + `playerViewportRect` over `playerPresentation(store.presentation)`, the reported `playerDisplay`'s size — `DEFAULT_PLAYER_DISPLAY` 1920×1080 until a player has said hello — and the scene). A white bar marks the map edge that is at the top of the TV (`tvTopEdgePoints`), a label says whether it is the whole map. While the player scale is locked (`isScaleLocked`: calibrated and not overview) and no canvas tool runs, the rectangle (a Konva `Group`, no fill so the DM's pixels are untouched) is draggable: every drag move clamps the centre onto the map and calls `setPresentation({ center })`, which the sync layer forwards at once; with a tool running, or a fitted map, it is a dashed, inert outline. The surface reports `data-player-center`, `data-player-rect` (`x,y,w,h`, rounded), `data-player-rotation` and `data-player-draggable`.
- Annotations (T011, ADR 0016): `AnnotationPanel` holds the **drawing tool** (`draw-mode-draw` / `draw-mode-erase`, `aria-pressed`; `draw-color` + palette `draw-swatch`s, `draw-width` slider 1–40 map px with `draw-width-value`, `draw-visibility` select `dm` | `all` for *new* strokes, **Clear drawings** `draw-clear` with the count), the **note tool** (**Add note…** `note-tool`, `aria-pressed` while placing; **Stop (Esc)** `annotation-stop` while either tool runs), the note list (`note-count`, `note-item` with `data-note-id` / `data-selected`, an `Open note <first line>` button that toggles the popover and a `Delete note <first line>` button `note-delete`) and the ping hint. The settings are DM-only UI state in `DmView` (`dm/annotationTool.ts`: `DrawToolSettings` `{ mode, color, strokeWidth, visibility }`, `DEFAULT_DRAW_TOOL_SETTINGS`, `ERASER_RADIUS_PX` = 10 screen px, `DRAW_PALETTE`), as is the open note's id (`selectedNoteId`, reset on a map switch, ignored once the note is gone). `DmTool` gains `draw` and `note`, exclusive with the others. `DmCanvas` takes `draw: DrawToolProps` (`{ settings, onStroke(points), onErase(point, radius), onCancel }`): the pen runs `map/fogGesture.ts` with the brush tool (thinned path, `FOG_MIN_STEP_PX`), previews the stroke in the overlay in the pen's colour and hands the flat points to `onStroke` on release (→ `AnnotationActions.addDrawing` with the current colour / width / visibility); the eraser calls `onErase` on every press and drag move with `ERASER_RADIUS_PX / scale` (→ `AnnotationActions.erase`: whole strokes within reach) and shows its circle under the pointer; Esc abandons a stroke or leaves the tool. `notes: NoteToolProps` (`{ placing, selectedId, onPlace, onSelect, onMove, onTextChange, onDelete, onCancel }`): while placing, a click on the map calls `onPlace` (→ `addNote` with empty text, the tool turns off and the popover opens); **note markers** (`NoteMarker`, pink pins of `NOTE_MARKER_RADIUS` = 9 screen px) are drawn by the DM canvas in the stage's *controls* layer — never by the shared stage — always clickable (toggle the popover; presses on a marker are `cancelBubble`d so tools do not see them) and draggable (`onMove` → `updateNote`); the **popover** is a DOM box (`note-popover` with `data-note-id`, positioned at `mapToScreen(viewport, note)` + an offset) with a textarea `note-text` (every change → `updateNote`, autosaved like any op), **Delete note** `note-popover-delete` and **Close** `note-popover-close`. `onPing(point)`: `MapStage`'s `onAltClick` — an Alt-click anywhere, whatever tool runs (the stage keeps that press from the pointer tool) → `AnnotationActions.ping` → `store.sendPing`; the canvas hands the store's DM-only `pings` to the stage so the DM sees the same pulse. The surface reports `data-drawing` (`draw` | `erase` | `false`), `data-draw-gesture` (`dragging` | `idle`), `data-note-tool` (`placing` | `none`), `data-note-open` (id or empty) and `data-notes`; hints are `draw-hint` / `note-hint`.
- Walls and doors (T101, ADR 0024): `DmCanvas` always draws the active map's `walls` in the stage's *controls* layer through `dm/WallLayer.tsx` — DM chrome like the note markers, never the shared stage: a `Group` named `walls` of one `Line` per segment (`name="wall"`, id `wall-<segment id>`, points = the endpoints in map pixels, `strokeScaleEnabled` off), a wall solid in `WALL_COLOR` at `WALL_STROKE_PX` (3 screen px). Since T103 a door is named `wall door` and drawn in `DOOR_COLOR`: closed, a solid bar at `DOOR_STROKE_PX` (6) with butt caps; open, a faint dashed line across the doorway (`OPEN_DOOR_STROKE_PX` 1.5, `DOOR_DASH`, `OPEN_DOORWAY_OPACITY`) plus a non-listening `door-leaf` line (id `door-leaf-<segment id>`) swung `OPEN_DOOR_SWING_DEG` (45°) clockwise about its first end by the pure `openDoorLeaf(from, to)`. The surface reports `data-walls` (the count), `data-wall-segments` (every segment as `kind:x1,y1,x2,y2`, a door followed by `:open` or `:closed`, `;`-separated, three decimals at most — `wallSegmentsAttribute`) and `data-doors-open`. Nothing in `map/` or `player/` imports the layer or reads a segment's endpoints (`player/boundary.test.ts`), so the player, which *holds* the walls, cannot draw one; the player view root reports only their count (`data-walls`) and how many doors are open (`data-doors-open`, T103).
- Wall and door tools, selection and editing (T102, ADR 0025): `DmCanvas` takes a `walls` prop (`WallToolProps`: `drawing`, the `WallToolSettings`, `selectedId`, `onSegment`, `onSelect`, `onMoveEndpoint`, `onCancel`). While `drawing` (tool `wall`), presses run the pure gesture machine `map/wallGesture.ts` (below) with a config built from the settings and the viewport scale (`grid` = the scene's while snapping is on, `snapThreshold` = `WALL_SNAP_PX / scale`, `minDrag` = `WALL_CLICK_THRESHOLD_PX / scale`); every committed segment goes to `onSegment` and the overlay draws the live preview (the placed vertices as dots, the segment from the last one to the pointer — in `DOOR_COLOR` for a door — and a ring at the snapped point under the pointer, `wall-snap-cursor`); a hint (`wall-hint`) says what to do. Esc ends a polyline or drag in progress, else `onCancel`; entering or leaving the tool, switching tools or maps resets the machine. With **no tool armed** (and Space up) the layer is interactive: every segment listens `WALL_HIT_PX` (12 screen px) wide — a constant `hitStrokeWidth`, because with `strokeScaleEnabled` off Konva draws the hit stroke unscaled too — and a click on a wall calls `onSelect` (a click on a door toggles it instead, below; an Alt-click is a ping), the selected segment gets a halo (`wall-highlight`, `WALL_SELECTED_COLOR`) and two draggable end handles (`wall-handle`, id `wall-handle-<segment id>-<start|end>`, `WALL_HANDLE_RADIUS_PX`); a handle follows the pointer through the same snapping (`snapWallPoint`; Shift on the drag skips it) with the segment redrawn live, and the drop calls `onMoveEndpoint(id, end, point)`; Esc calls `onSelect(null)`. The surface reports `data-wall-tool` (`none` | `wall` | `door`), `data-wall-gesture` (`idle` | `drawing` | `dragging`), `data-wall-snap` and `data-wall-selected`. Konva redraws a layer's hit graph on the next animation frame after its nodes start listening, so a click within that frame of putting a tool down misses (the e2e waits a frame).
- Doors in play (T103, ADR 0024 as amended): `WallToolProps` gains `onToggleDoor(id)` and `focus?: WallFocus` (`{ id, nonce }`). `DmCanvas` computes `doorsClickable` — `walls` given, no wall drawing, no grid alignment (both click on grid corners, where doors end), Space up — reports it as `data-doors-clickable` and hands it to `WallLayer`: while it holds, a door's node (and the `walls` group) listens whatever tool is armed, with the `pointer` cursor on hover; plain walls still listen only with no tool armed. A primary, non-Alt press on a door is `cancelBubble`d and remembered, and so is its release (a window `mouseup` / `touchend` forgets a press released elsewhere), so the stage's `pointerTool` — fog, pen, eraser, note placement — never sees that click while a drag that merely ends on a door still reaches it; Alt-clicks (pings) and middle-button presses (pans) bubble as before. The click calls `onToggleDoor` and never `onSelect`: `DmView`'s `toggleDoor` reads the door from the store and dispatches `map/door-set-open` with the opposite state (the panel's `door-toggle` calls the same function). The panel's `door-select` calls `DmView`'s `focusWall`, which selects the door and issues a new `focus` nonce; `DmCanvas` answers each new nonce once by centring the viewport on the segment's middle (`viewport.ts: centerOn`; an unknown id or an unmeasured container does nothing, and later moves of the segment do not re-centre). Every `onOps` listener of the store sees the op, which is where T106 re-runs vision on a door change.
- Tokens (T010, ADR 0015): `TokenPanel` lists the active map's tokens (`token-count`, `token-item` with `data-token-id` / `data-selected` / `data-hidden`, a `Select <name>` button each), adds a disc (**Add token**, `token-add`) or an image token (`token-image-input`; errors in `token-error`) placed at the centre of what the TV shows (`resolvePlayerView(...).center`) and snapped, and edits the selected one (`token-editor`: `token-name`, `token-badge` (≤ `TOKEN_BADGE_MAX_LENGTH` = 3 chars), `token-color` (discs only), `token-size` 1×1..4×4, `token-vision` (**Vision (cells)**, a number input 0–`TOKEN_VISION_MAX` (60), step 1: a typed value is rounded to whole cells and clamped by `vision.ts: clampTokenVision`, an emptied field dispatches nothing — T105), `token-snap`, `token-hidden`, **Remove token** `token-remove`, **Done** `token-deselect`) through `TokenActions`. The selection is DM UI state in `DmView` (`selectedTokenId`: reset on a map switch, ignored once the token is gone); `DmView` hands `DmCanvas` a `tokens: TokenTool` (`{ selectedId, onSelect, onMove }`; the canvas adds `onDragMove` for its vision preview, T106) which the canvas passes to the stage only while no pointer tool runs (`data-token-tool` `active` | `none`), so a click on a token selects it and a drag moves it — the layer clamps and snaps live (`placeToken`) and `onMove` becomes `TokenActions.move` → one `map/token-update` on release, after which the view's vision actions reveal what a seeing token sees (T106, `state/visionActions.ts` below). The canvas reads the active map's token images from the database (`useAssetBlobs` over `tokenImageAssetIds(scene)`) and hands them to the stage as `tokenImages`. jsdom cannot hit-test Konva nodes, so a drag is unit-tested by moving a token node and firing its `dragmove` / `dragend` (T106: `map/MapStage.test.tsx`, `dm/DmCanvas.test.tsx`, `dm/DmView.test.tsx`), and the placement maths on its own.
- **Single source of truth is the DM window Zustand store.** The player window is a dumb mirror: it applies sync messages received over a BroadcastChannel and renders. It never mutates state. Message schema lives in app/src/state/sync.ts (typed, versioned). Full-state snapshot on player connect; deltas after (fog ops are sent as operations, never bitmaps). Binary assets (map images) are pushed by the DM as `asset` messages on the same channel (ADR 0008); the player never reads storage. How the player should present scenes on its display (calibration, overview, ruler screen — ADR 0011; pan centre, rotation, blackout, splash — ADR 0014) travels as an unsequenced `presentation` message; the player's `hello` carries its `DisplayInfo` so the DM can look up that display's calibration. **DM-only annotations never leave the DM window** (T011, ADR 0016): the publisher filters every snapshot and delta (`annotations.ts: sharedStateForPlayer` / `opsForPlayer`), so notes and DM-only drawings are in the DM's state and the saved document but never on the channel; a **ping** is an unsequenced `ping` message (an event, never in a snapshot). **Walls and doors do cross the channel** (T101, ADR 0024): the player needs them for vision (T107), so `MapScene.walls` is in every snapshot and the wall ops (`map/wall-set`, `map/wall-remove`, `map/walls-clear` and T103's `map/door-set-open`) pass the filter untouched — the player holds them and, like hidden tokens (ADR 0015), has no code that draws them. So do the vision fields (T105, ADR 0026): `Token.vision` rides in tokens and `map/token-update` patches, and `map/set-vision-dim` passes the filter untouched, because the player computes the dimmed overlay from them (T107).

### State & sync modules (`app/src/state/`)
- `model.ts` — scene-level data model: `MapScene` (id, name, `imageAssetId | null`, `backgroundColor`, size (`width` / `height` in map pixels — the image size *as turned*), `imageRotation` (`Rotation`: how far the stored image asset is drawn turned clockwise; the asset is never re-encoded — T017, ADR 0021), `grid`, fog: `fogMaskAssetId` (the base PNG, null = fully fogged) + `fogOps` (the op log) + `fogOpsFrom` (history index of `fogOps[0]`; ADR 0012), tokens, annotations, `walls` (wall and door segments, T101, ADR 0024), `visionDim` (`VisionDim` = `auto` | `on` | `off`, `VISION_DIMS`: whether the player dims revealed areas no token currently sees — T105, ADR 0026)), `GridSettings` = `GridGeometry` (`cellSize`, `offsetX`, `offsetY` in map pixels; any offset is legal, renderers wrap it into the first cell) + one `GridStyle` (`visible`, `color`, `opacity` 0..1) per `GridView` (`dm`, `player`; ADR 0010), `Token` (`id`, `name`, `appearance` `{ type: "disc", color }` | `{ type: "image", assetId }`, `badge`, `x`/`y` = top-left in map px, `size` 1..4 cells, `snapToGrid`, `hidden` = DM-only, `vision` = vision radius in whole cells, 0 = none; a hidden token keeps it — T105), `Annotation`, `AssetId`, `AssetKind` (`map-image`, `token-image`, `fog-mask`, `splash-image`), `SCHEMA_VERSION` (10), plus structural type guards (`isToken` and `isTokenPatch` share one validator per token field — `vision` is `isTokenVision`, a safe integer ≥ 0, so a patch with a negative or fractional vision is refused; `isVisionDim`; `isMapScene` requires `walls` and checks every segment, and requires a legal `visionDim`). Binary data is referenced by `AssetId`, never embedded.
- `walls.ts` — walls and doors, pure and shared by both windows (T101, ADR 0024): `WallSegment` = `{ id, x1, y1, x2, y2, kind: "wall" }` | `{ …, kind: "door", open }` (map pixels, any angle; `DoorSegment` / `PlainWallSegment`), `WALL_KINDS` + `isWallKind`, `isWallSegment`, `WallPatch` (`{ x1?, y1?, x2?, y2?, kind?, open? }`) + `isWallPatch` (known fields only, each well-formed; `{}` is valid), `segmentLength`, `segmentPoints` (the two endpoints for the maths modules), `isBlocking` (a wall always, a door while closed), `isDoor` / `doorsOf` / `openDoorsOf` (the open ones, which both windows count as `data-doors-open` — T103), constructors `createWall`, `createDoor` (closed unless asked), `cloneWall`, `wallsEqual` (id, kind, endpoints in order, a door's `open`), `wallListsEqual`, `patchWall` (same object when nothing changes; wall → door gains `open`, door → wall drops it), `findWall`. Segments record nothing about how they were drawn: T102's tools and v3's wall tiles emit the same shape.
- `vision.ts` — vision fields, pure and shared by both windows (T105, ADR 0026): `seeingTokens(scene)` (the tokens with `vision > 0`, hidden ones included, in document order), `mapUsesVision(scene)` (`visionDim` resolved: `on` always, `off` never, `auto` while any token on the map has vision — what T107 dims by, so a manual-fog map looks as it always did), `tokenCentre(token, cellSize)` (the footprint's centre, the point T106 sees from), `TOKEN_VISION_MAX` (60, the token editor's bound; the model accepts any whole number ≥ 0) and `clampTokenVision(cells)` (rounded to whole cells, clamped to 0..60, NaN → 0). T105 added the data and those helpers; T106 adds `tokenVisionPolygon(scene, token, segments?)`, what a token sees: `map/visibility.ts: visibilityPolygon` from `tokenCentre` within `visionRadiusPx(vision, cellSize)`, blocked by `blockingSegments(walls)` unless the caller passes its own segments, `[]` without vision — shared by the reveal on drop, the DM canvas's drag preview and the overlay of `map/visibleArea.ts` (T107).
- `visionActions.ts` — vision on the DM side (T106, ADR 0026): `createVisionActions(store, { apply?, schedule? })` → `revealFor(mapId, tokenId)` (one `apply` with `visionRevealOp(scene, token)`, a `polygon` reveal of `tokenVisionPolygon` with `fog.ts: fogFeatherPx(cellSize)`; false, dispatching nothing, for an unknown map or token, no vision, an empty polygon, or when `alreadyRevealed(log, op)` — a reveal-all or an identical polygon reveal follows the log's last op that hides), `revealAll(mapId)` (the same for every `seeingTokens(scene)` in **one** `apply` call: one seq, one delta, one undo step), `start()` / `stop()`. Started — `DmView` runs it as an effect over `FogActions.apply`, so reveals compact, and takes an injected `visionActions` in tests — it watches `store.onOps`: a `map/token-update` with `x` or `y` in its patch (a drop) or a `vision` above 0 queues that token, a `map/door-set-open` either way queues the map's seeing tokens; nothing else triggers (not a map switch, a load, a token add or a wall edit). The queue is flushed per map by `schedule`, a microtask by default, so each reveal is a dispatch of its own after the trigger's has reached every listener (the sync publisher sees them in order), and every op the actions' own `apply` sets off is ignored (no feedback loop). Closing a door re-hides nothing: the narrower views are reveals too. Off-limits to `src/player/**`.
- `fog.ts` — fog operations (ADR 0012, ADR 0013), pure and shared by both windows: `FogMode` (`reveal` | `hide`), `FogShape` (`rect` | `circle` | `polygon` (flat points, ≥ 3) | `stroke` (flat points ≥ 1 + `radius`: a brush drag, round caps and joins; one point is a disc) | `rects` (flat `[x, y, w, h, ...]`, a union of rectangles: what grid snapping produces), all in map pixels), `FogOp` (`{ type: "fill", mode }` | `{ type: "shape", mode, shape, feather? }` — `feather` is the soft-edge width in map px, only present when positive), constructors `fogFill`, `fogShape(mode, shape, feather?)`, `rectShape(a, b)` (any two corners → normalised rect), `strokeShape`, `polygonShape`, `rectsShape`, `fogShapeBounds`, `cloneFogOp`, and guards `isFogOp`/`isFogShape`.
- `shared.ts` — `SharedState` (the only state the player ever sees — bar DM-only annotations, which the publisher strips (T011): `campaignName`, `maps`, `activeMapId`, `splashImageAssetId` (the campaign's splash image, null = none chosen; - `sceneRotation.ts` — turning a scene in quarter turns, pure and shared by both windows (T017, ADR 0021): `RotationDegrees` (`90 | 180 | 270`, clockwise; `isRotationDegrees`), `rotatedSceneSize` (a quarter turn swaps the sides), the point transform `rotatePoint(p, size, degrees)` for the old size `(W, H)` — 90°: `(H − y, x)`, 180°: `(W − x, H − y)`, 270°: `(y, W − x)` — plus `rotatePoints` (flat lists) and `rotateRect` (corners turned, renormalised); `rotateGrid` (cell size unchanged, origin turned as a point and wrapped into the first cell: the turned scene's line set is the turned line set, a vertical line becoming a horizontal one), `rotateToken` (the footprint's centre is turned and the top-left recomputed; a snapped token stays on the turned grid), `rotateAnnotation` (note position, drawing points), `rotateWall` (both endpoints as points; kind and `open` kept — T101), `rotateFogShape` / `rotateFogOp` (`rect` / `rects` corners renormalised, `circle` centre, `polygon` / `stroke` points, radii and `feather` kept, `fill` untouched) and `rotateScene(scene, degrees, fogMaskAssetId)` (all of the above; `imageRotation` advances, `fogOpsFrom` is untouched, the given mask id replaces the old). - `rotation.ts` — `Rotation` (`0 | 90 | 180 | 270`, degrees clockwise on screen), `isRotation`, `normalizeRotation`, `rotateClockwise` / `rotateCounterClockwise`, `isQuarterTurn` (swaps width and height) and `mapEdgeAtTop` (which map edge lies along the top of the TV: a clockwise quarter turn brings the left edge up). Pure; shared by both windows (T009).
- `calibration.ts` — physical calibration, all pure (ADR 0011): `DisplayInfo` (`width`, `height` in CSS px, `pixelRatio`, `left`, `top`) + `readDisplayInfo(window)` + `displayKey` (the settings key, `WxH@dpr+left,top`); `CellUnit` (`inch` | `mm25`) and `cellInches`; `DisplayCalibration` (`pxPerInch` in CSS px, `method` `square` | `diagonal`, `updatedAt`); `DisplayRotation` (`{ rotation, updatedAt }`: the player view rotation remembered for a display, a sibling record of its calibration — T019, ADR 0023) with `isDisplayRotation`; derivations `pxPerInchFromSquare(sizePx, unit)` and `pxPerInchFromDiagonal({ diagonalInches, widthPx, heightPx, pixelRatio })` (null outside 10–600 px/in); `lockedScale(pxPerInch, unit, cellSizePx)` = the player stage scale; `PlayerPresentation` (`{ pxPerInch | null, cellUnit, overview, target, rotation, center: MapPoint | null, blackout, splash }`, what the `presentation` message carries; T009 added the last four — `center` is the map point at the middle of the player display, null = the map's centre) with `presentationMode` → `calibrating` | `calibrated` | `overview` | `uncalibrated` (blackout and splash are overlays, not modes), `isPlayerPresentation`, `playerPresentationEqual` (centre by value), `clonePlayerPresentation`; `PresentationState` (the DM-only store slice: `playerDisplay`, `calibration`, `cellUnit`, `overview`, `target`, `rotation`, `center`, `blackout`, `splash`, plus the DM-only preference `splashOnSwitch`), `playerPresentation(state)` and `presentationForMapSwitch(state, nextActiveMapId)` (drops the centre; raises the splash when `splashOnSwitch` and a map is being shown).
- `calibrationSession.ts` — DM-side plumbing over a store + database: `createCalibrationSession(store, db)` → `start()` (loads the cell unit; loads a display's calibration **and its remembered rotation** whenever `presentation.playerDisplay` changes, dropping stale loads — a display without a rotation record is put at 0; and, while a display is known, writes every change to `presentation.rotation` under that display's key (T019) — a turn while no display is known is not saved, and a DM turn wins over a load still in flight), `save(calibration)` / `clear()` (persist for the connected display, then apply; false when no display is known; `clear` leaves the rotation alone), `setCellUnit`. Off-limits to `src/player/**`.
- `store.ts` — the DM store (`createTableStore`, app-wide `tableStore`, `useTableStore` hook). Shared state changes only via `dispatch(...ops)`, which applies the reducer, bumps `seq` by one per dispatch and notifies `onOps` listeners. `campaignId` (DM-only) names the persisted document the shared state belongs to; `openCampaign(campaign)` sets it and applies `campaign/replace` in one commit, `closeCampaign()` clears it. `presentation` (DM-only, `PresentationState`) changes via `setPresentation(patch)` and `setPlayerDisplay(display)` (a different display drops the loaded calibration); neither bumps `seq`. A dispatch whose ops change `activeMapId` also applies `presentationForMapSwitch` in the same commit (the pan centre belongs to the active map; T009), before op listeners run; one carrying a `map/rotate` of the active map applies `presentationForMapRotate` (drops the centre only — a turn is not a switch, so the splash is not raised; T017). `pings` (DM-only, transient; T011) is the list of recent pings the DM sent, for the DM canvas's own pulse: `sendPing(ping)` adds it (`addPing`; a duplicate id is ignored) and notifies `onPing` listeners (the sync layer posts it); not sequenced, not shared. **`src/player/**` may not import this module** (ESLint `no-restricted-imports` + `boundary.test.ts`).
- `sync.ts` — the protocol (ADR 0006, ADR 0008, ADR 0011, ADR 0016): `PROTOCOL_VERSION`, `SYNC_CHANNEL_NAME`, message types `hello` (optionally with the player's `display`) / `snapshot` / `delta` / `asset` (`{ id, kind, mime, data: base64 }`, unsequenced) / `presentation` (`PlayerPresentation`, unsequenced, latest wins) / `ping` (one `Ping`, unsequenced, never in a snapshot; T011), constructors, `encodeMessage` (JSON string) and `decodeMessage`/`validateMessage` (never throw; reject other versions, unknown types and bad shapes).
- `transport.ts` — `SyncTransport` interface (`post`, `onMessage`, `close`). `createBroadcastTransport` wraps a BroadcastChannel; `createMemoryHub` is the in-test replacement with the same fan-out (never echoes to the sender); `createNullTransport` is used where BroadcastChannel is missing.
- `mirror.ts` — the player-side `MirrorState` (`connecting | synced`, `seq`, `shared | null`, `assets: Record<AssetId, Blob>`, `presentation: PlayerPresentation`, `pings: Ping[]`) and the pure `reduceMirror(mirror, message)`: snapshots always replace; a delta applies only if `seq === mirror.seq + 1`; stale/duplicate deltas are ignored; a gap, or a delta before any snapshot, sets `resync` so the caller re-requests a snapshot — as does a **DM** `hello`, so a restarted DM learns this player's display. `asset` messages are decoded into `assets` whenever they arrive (undecodable data is ignored); after every snapshot/delta, assets the state no longer references are dropped. `presentation` messages replace `presentation` (same object if identical); snapshots/deltas carry it through. `ping` messages go through `addPing` into `pings` whatever the status (same object for a duplicate id); snapshots/deltas carry the list through (T011).
- `dmSync.ts` — `startDmSync(store, transport, { assets? })`: on start sends `hello(dm)` + a snapshot (so already-open players catch up) + the presentation, answers every player `hello` with a snapshot + presentation, forwards each dispatch as one `delta`, and sends a `presentation` whenever the store's `playerPresentation` changes. A player hello carrying a `display` is recorded with `setPlayerDisplay` (DM-only bookkeeping; the only thing a received message may write). Nothing received can mutate the *shared* state. With an `AssetSource` it also pushes every referenced asset not yet sent this session (queued, one at a time, `assetIdsForPlayer` order) after the snapshot/delta, and re-sends all of them on a `hello` from a client id it has not served yet (a known player re-announcing gets only the snapshot + presentation). **Every snapshot goes out as `sharedStateForPlayer(shared)` and every delta as `opsForPlayer(ops)`** (T011, ADR 0016): DM-only annotations never reach the channel, and the seq still advances by one per dispatch. Every `store.sendPing` is posted as one `ping` message.
- `playerSync.ts` — `startPlayerSync(mirror, transport, { display? })` → `{ stop, announce }`: sends `hello(player, id, display?.())` on start, whenever `reduceMirror` asks for a resync, and on `announce()`; writes decoded messages into the mirror. **The player only ever sends `hello`.**
- React bindings: `dm/useDmSync.ts` (DM view; passes an `AssetSource` backed by `getAsset`) and `player/usePlayerSync.ts` (player view) create the transport inside an effect so StrictMode's double mount gets a fresh channel; both views accept an injected `createTransport` for tests. `usePlayerSync` also takes a `readDisplay` (default: `window.screen`, undefined where it is unknown, e.g. jsdom) and re-announces when the display key changes — checked on `resize` and every `DISPLAY_POLL_MS` (1 s), because the popup opens on the laptop and is dragged to the TV afterwards. `PlayerView` exposes `data-sync-status` / `data-sync-seq` / `data-active-map-id` / `data-view-mode` / `data-rotation` / `data-view-center` / `data-blackout` / `data-splash` on its root for e2e assertions.
- Reconnect: a reloaded player window is simply a new endpoint; its `hello` fetches a full snapshot and deltas resume from that `seq`. A player opened before the DM stays `connecting` until the DM's start-up snapshot arrives; it then re-announces so the DM learns its display and sends the matching calibration.

### Persistence modules (`app/src/state/`, ADR 0007)
- `campaign.ts` — the persisted document `Campaign = { schemaVersion, id, name, createdAt, updatedAt, state: SharedState }`, `CampaignSummary` (what the manager lists), `newCampaign`, `isCampaign`, and `migrateCampaign` (never throws; brings older documents to `SCHEMA_VERSION`, reports `newer-schema` / `invalid`).
- `db.ts` — the Dexie database `TableMapDb` (`getDb()` is the app-wide instance; tests construct their own with a unique name). Tables: `campaigns` (documents, JSON only; indexed by `name`, `updatedAt`), `assets` (`{ id, campaignId, kind, blob }` — map images, token images, fog masks as Blobs), `settings` (key/value: last opened campaign; later, per-display calibration).
- `persistence.ts` — async functions over a `TableMapDb`: `listCampaigns`, `createCampaign`, `loadCampaign` (migrates; throws `CampaignLoadError` for corrupt/newer documents), `saveCampaign`, `saveCampaignState` (what autosave calls; false if the campaign was deleted meanwhile), `renameCampaign`, `deleteCampaign` (also deletes its assets and the last-opened pointer), `putAsset`/`getAsset`/`deleteAsset`/`listAssetIds`, `getLastCampaignId`/`setLastCampaignId`, `getDisplayCalibration`/`setDisplayCalibration` (settings row `calibration:<displayKey>`; null clears; unreadable rows read as null), `getDisplayRotation`/`setDisplayRotation` (settings row `rotation:<displayKey>` holding a `DisplayRotation`; 0 deletes the row, and a missing or unreadable row reads as 0 — T019), `getCellUnit`/`setCellUnit` (settings row `cellUnit`, default `inch`), and `resolveStartupCampaign` (last opened → most recently updated → new "Untitled campaign"; unreadable documents are skipped).
- `autosave.ts` — `startAutosave(store, save, { debounceMs })`: subscribes to the DM store; any change to `shared` while `campaignId` is set schedules a write of the latest state after the debounce (default 400 ms); bursts coalesce; writes are serialised; opening another campaign or closing flushes first; `flush()`/`stop()` for unmount and `pagehide`. Pure logic, no IndexedDB.
- `session.ts` — `openStoredCampaign(store, db, id)` and `bootstrapCampaign(store, db)` (load-on-start; no-op when a campaign is already open; concurrent calls share one promise so StrictMode's double effect cannot create two default campaigns).
- `campaignArchive.ts` — export / import as one zip (T012, ADR 0017). `exportCampaign(db, id, { now? })` → `{ blob (application/zip), fileName, assetCount, missingAssetIds }`: loads the document (migrating, as any load does), collects `referencedAssetIds(state)` (unreferenced assets are not exported; referenced ones absent from storage are reported and left out) and writes `campaign.json` — the **envelope** `{ format: "tablemap-campaign", formatVersion: 1, exportedAt, campaign: Campaign, assets: [{ id, kind, type, path }] }`, DEFLATE — plus one file per asset under `assets/` (STORE: images are already compressed). Asset file names are **generated**, `archiveAssetPath(index, kind, type)` = `assets/0001-map-image.png` (1-based index, kind, extension from the MIME type, `bin` for unknown types), never taken from ids or names, so they are ASCII, short, unique on case-insensitive file systems and free of reserved characters; the manifest maps ids to paths. `archiveFileName(campaignName)` gives the download name (`<ASCII name>.tablemap.zip`, `campaign` when nothing is left, Windows reserved base names prefixed). `importCampaign(db, source: Blob | ArrayBuffer | Uint8Array, { newId? })` → `{ campaign, idChanged, remappedAssetIds, assetCount }`: opens the zip with CRC checks, reads and validates the envelope (format marker, `formatVersion` ≤ this build's, manifest entries with known kinds and paths matching `^assets/[A-Za-z0-9][A-Za-z0-9._-]{0,127}$` — no separators, no `..`, no leading dot, no duplicates), runs the document through `migrateCampaign` (older schemas come forward, newer ones are refused), reads every manifest file into a Blob of the recorded type, then writes the campaign and its assets in **one Dexie transaction**. It never overwrites: a campaign id already in storage gets a fresh id (`idChanged`) and every asset id already in the `assets` table (whoever owns it) is re-keyed with the document's references rewritten by `maps.ts: remapAssetIds` — on an empty database ids are kept, so the round trip is byte-equivalent. Every failure is a `CampaignImportError` with a `reason` (`not-a-zip`, `no-document`, `bad-json`, `not-a-campaign`, `newer-format`, `bad-manifest`, `missing-asset`, `bad-asset`, `invalid`, `newer-schema`) and a message fit for the UI; nothing is written on failure. A document referencing an asset the archive lacks imports anyway (same as storage: a missing fog base renders fully fogged, a missing image as an error). Off-limits to `src/player/**`.
- `src/player/**` may not import `db`, `persistence`, `autosave`, `session`, `calibrationSession`, `fogActions`, `fogHistory`, `splashActions`, `tokenActions`, `visionActions` (T106), `annotationActions` or `campaignArchive` either (same ESLint rule + boundary test): the player never touches storage or writes state. The boundary test also asserts that no player source calls `sendPing` or mentions notes (`kind === "note"`, `NoteAnnotation`, `notesOf`, `NoteMarker`): notes are DM-only and there is no code in the player that could draw one (T011). Likewise (T101) neither `src/player/**` nor `src/map/**` imports `dm/WallLayer.tsx` (`WallLayer`, `WallNode`) or reads a wall segment's endpoints: walls are data on the player, drawn only by the DM canvas.

## Rendering (`app/src/map/`, shared by both views; imports neither `dm/` nor the DM store)
- Konva stage with layers bottom-to-top: map image -> grid -> underlay (DM only) -> dim (T107: only while the map uses vision) -> tokens -> annotations (drawings) -> fog -> tool overlay -> pings (while one plays) -> controls. Walls and doors are *not* a stage layer: the scene carries them, but only the DM canvas draws them, in its controls (T101, ADR 0024).
- `MapStage.tsx` — the react-konva stage. Props: `scene`, decoded `image` (or null), container `size`, `viewport` (`{ x, y, scale, rotation? }` = stage transform; rotation in degrees clockwise, applied by Konva after the scale — the player view's quarter turns, T009), `gridView` (`dm` | `player`: which of the scene's two grid styles to draw and how opaque the fog is — the DM canvas passes `dm`, the player view `player`), `interactive` (wheel zooms around the pointer, dragging the stage pans; the new viewport is reported via `onViewportChange` — the caller owns it), `pointerTool` (`{ onDown, onMove, onUp, onDoubleClick? }` receiving map-pixel points, each with the `PointerModifiers` (`{ shift }`) of the event, from the stage's mouse/touch events — `onDoubleClick` on Konva's `dblclick` / `dbltap`, a second release within its 400 ms click window (T102); while set, drag-pan is off but wheel zoom stays), `panOverride` (T018: while true every press pans the stage by hand instead of reaching the tool or Konva's drag; a middle-button press does the same without it; `data-panning` while one runs), `overlay` (Konva nodes drawn in a top layer, in map coordinates), `fogOverlay` (Konva nodes drawn inside the fog layer after the mask, in map coordinates — a node with `globalCompositeOperation="destination-out"` punches a live preview through the fog; T008), `dimOverlay` (Konva nodes drawn inside the dim layer after its cut-outs, in map coordinates, only while the map dims — a `destination-out` node lifts the dim there; T107), `controls` (Konva nodes in a *listening* layer above everything, in map coordinates — the DM's player-viewport frame and note markers; a draggable node here takes the drag instead of the stage; T009), `underlay` (Konva nodes in a *listening* layer beneath the tokens, in map coordinates — the DM's invisible player-viewport drag handle, so that a drag starting on a token inside the TV area moves the token and one anywhere else inside the rectangle pans the player view; Konva hit-tests a fill-less shape's whole interior, so a handle above the tokens would take every drag inside it; T013, ADR 0018), `fogBase` (the Blob of the scene's fog base PNG, undefined until available), `tokenImages` (Blobs of the scene's image tokens by asset id; T010), `tokenTool` (`TokenTool`: DM selection + drag, see `TokenLayer.tsx`), `pings` (recent pings; the active ones for this scene are animated; T011) and `onAltClick(point)` (a click with Alt held, in map pixels — the DM's ping gesture; the stage keeps such a press from the pointer tool; T011). Layer 1: a `Rect` in `scene.backgroundColor` (all of a blank map) under the `Image` (node name `map-image`, drawn at the asset's own size — `imageAssetSize(scene)` — with `rotation = scene.imageRotation` at `rotatedImagePlacement(...)`, so the turned image covers exactly `[0, width] × [0, height]`; T017, ADR 0021 — the scene's rotation is a document property, applied inside the stage, while the viewport's `rotation` (the player's TV rotation) is the stage transform on top); layer 2 (only if the chosen style is visible): the grid as one `Shape` (`strokeScaleEnabled=false` so lines stay 1 px at any zoom); the underlay layer when given; layer 3 (always): the tokens (`TokenLayer`); layer 4 (always): the annotations (`AnnotationLayer`); layer 5 (always): the fog mask canvas as a Konva `Image` at `FOG_ALPHA[gridView]` (0.5 dm, 1 player); then the overlay layer when given, the ping layer (`PingLayer`) while a ping plays, and the controls layer when given. The wrapper exposes `data-map-id`, `data-map-name`, `data-image-status` (`none | waiting | loading | loaded | error`), `data-image-rotation` (the scene's `imageRotation`), `data-map-size` (`width,height`, the turned size), `data-scale`, `data-viewport-x` / `data-viewport-y` (the stage translation, so e2e can map map-pixel points to screen), `data-rotation`, `data-grid-view`, `data-grid-visible`, `data-tool`, `data-fog-status` (`ready | bridged | waiting`, see below), `data-fog-ops` (log length), `data-fog-history` (`fogOpsFrom + log length`, the map's total fog op count — what e2e watches to time a reveal), for tokens `data-tokens` (count), `data-tokens-shown` (drawn by this view), `data-tokens-fogged`, `data-tokens-hidden`, `data-token-selected`, and for annotations `data-annotations` (the scene's count as this window knows it — the player never knows the DM-only ones), `data-annotations-shown` (drawings this view draws) and `data-pings` (active pulses) for tests.
- Annotations (T011, ADR 0016): `AnnotationLayer.tsx` draws `drawingsForView(scene.annotations, view)` between the tokens and the fog as round-capped `Line`s in map pixels (a one-point stroke is a `Circle` dot of the stroke's width); it draws drawings only — notes are DM chrome drawn by `DmCanvas` in the controls layer, so nothing in `map/` or `player/` can put a note on the TV. Under the fog, a shared stroke in a fogged area is as hidden as the map. `PingLayer.tsx` draws each active ping above the fog in a non-listening layer: a dot (`PING_DOT_RADIUS` 7 screen px, solid for 70 % of the pulse then fading) and two rings expanding from `PING_RING_MIN` (8) to `PING_RING_MAX` (60) screen px, the second a quarter period behind, fading as they grow; everything is a function of `pingProgress(ping, now)` and sizes are divided by the stage scale so a pulse looks the same at any zoom. `usePings.ts` — `usePings(pings, mapId)` → `{ active, now }`: `now` advances every animation frame while any ping is playing (one `requestAnimationFrame` loop, stopped once the state's `now` has passed the last pulse's end; a `setTimeout` at that end guarantees the last update even when frames stop in a hidden window) and the stage recomputes `activePings` from it; an idle stage costs no frames. Whether the clock runs is decided from the state's `now`, not a fresh `Date.now()` in render — otherwise a render a few ms after the pulse's end, with the state still earlier, would stop the clock with the pulse still drawn (a race the e2e caught).
- Tokens (T010, ADR 0015): `TokenLayer.tsx` draws `scene.tokens` between the grid and the fog: a disc (`Circle` in the token's colour, 92 % of the footprint, with the badge as centred bold `Text`) or an image (`useImageElement` per token, fitted to cover the footprint and clipped to a circle by a `Group` `clipFunc`, badge in a small pill bottom-right; a grey disc until the Blob is there). `visibility` comes from the stage: `sceneTokenVisibility(scene, fog.isFogged)`, memoised on the tokens, the grid, the map size and the fog handle's `isFogged` (a new function after every mask update — `useFogMask` now returns `version` and `isFogged`, which reads the rendered mask through `fogRaster.ts: createFogSampler` — a 1 × 1 scratch canvas with `willReadFrequently` that receives one pixel by `drawImage` and is read with `getImageData`, so the big mask canvas is never read back directly; while the mask is `waiting` every pixel counts as fogged). The **player** view draws only `visible` tokens (neither `hidden` nor `fogged`: every cell of the footprint must be revealed, sampled at the cell centres). The **DM** view draws them all: fogged ones sit under the half-opaque fog (dimmed) with a thin dashed box, hidden ones at `HIDDEN_TOKEN_OPACITY` (0.45) with a dashed ring, the selected one with a highlight box. With a `tool` the layer listens: a token `Group` is draggable, `onDragMove`/`onDragEnd` run `placeToken` (live clamp + snap), every move reports the would-be top-left to the tool's optional `onDragMove(id, topLeft)` (T106: the DM canvas's vision preview) and the end reports `onMove(id, topLeft)`; click / drag start call `onSelect(id)`. Without one (player, or a canvas tool running) the layer is non-listening.
- `viewport.ts` — pure math: `fitToView` (contain + centre with padding), `centerAtScale` (dictated scale, map centred), `zoomAt` (keeps the map point under the pointer fixed; scale clamped to 0.05–8), `wheelZoomFactor`, `panBy`, `centerOn(viewport, point, view)` (same scale and rotation, the map point mid-view — the Walls panel's door list, T103), `rotateVector` (clockwise, exact for quarter turns), `screenToMap`/`mapToScreen` (honour the viewport's `rotation`). `playerView.ts` (T009, ADR 0014) — how the player display shows a scene, shared by both windows: `PlayerView` = `{ center, scale, rotation }`; `resolvePlayerView(presentation, scene, display)` (scale = `lockedScale` while `isScaleLocked` — calibrated and not overview — else fit to the *rotated* display via `rotatedSize`; centre = the presentation's centre clamped onto the map (`clampCenter`) while locked, else the map's centre — a fitted map has nowhere to pan); `playerStageTransform(view, display)` → the stage `Viewport` that puts the centre mid-display, rotated (`display / 2 − rotate(center × scale)`); `playerViewportRect(view, display)` → the inverse: the axis-aligned map rectangle the display shows (`display / scale`, width and height swapped by a quarter turn, centred on `center`), which the DM drags; `rectCenter`; `DEFAULT_PLAYER_DISPLAY` (1920×1080). Rotation never changes the scale, so a calibrated cell is the same number of screen pixels whichever way the map is turned. `grid.ts` — `normalizeOffset`, `gridLinePositions`/`gridLines` from `GridGeometry` (offset wrapped into the first cell), `nearestGridCorner(p, grid)` (the corner lattice point nearest to a map point, on or off the map — the wall tools' snap target, T102), and `alignGridToSquare(a, b)`: two opposite corners of one printed square (any order, either diagonal) → `{ cellSize, offsetX, offsetY }`; cell size is the mean of the box's width and height, offset is the box's top-left wrapped into the first cell; null below `MIN_ALIGN_CELL_SIZE` (4 px). `alignment.ts` — the alignment tool's pure state machine (`reduceAlignment(state, event)`: `idle` → `dragging` on press; release after ≥ `minDrag` completes, a shorter release is a click and moves to `second`, where the next press completes; `cancel` from anywhere; `alignmentBox` gives the preview rectangle). `minDrag` is `ALIGN_CLICK_THRESHOLD_PX` (6 screen px) divided by the viewport scale.
- `useImageElement.ts` — Blob → object URL → decoded `HTMLImageElement` (revoked on change/unmount). `useContainerSize.ts` — ResizeObserver-backed element size.
- DM (`dm/DmCanvas.tsx`): reads the active map's image Blob and fog base Blob from the database (`dm/useAssetBlob.ts`, which also provides object URLs for the panel thumbnails), fits the viewport whenever the active scene changes or changes size (a map rotation, T017), then leaves pan/zoom to the user; the surface reports `data-map-size` and `data-map-rotation`. **Vision preview** (T106, ADR 0026): the canvas wraps the view's `TokenTool` with `onDragMove`, keeps the dragged token's latest would-be top-left in a ref and, at most once per animation frame, computes `state/vision.ts: tokenVisionPolygon` there (none for a token without vision), drawn like the fog reveal preview — `PREVIEW_TINT.reveal` in the overlay (node `vision-preview`) and punched through the fog layer (`vision-preview-reveal`) and, on a map that dims, through the dim layer via `dimOverlay` (`vision-preview-lit`, T107). The drop (before `onMove` is passed on), losing the token tool (a pointer tool armed, Space held) or a map switch clears it; `data-vision-preview` reports its vertex count, 0 for none. The canvas dispatches nothing for it: the reveal is the view's vision actions'. Player (`PlayerView`): takes both Blobs from the mirror's `assets`, shows the idle campaign title when no map is active, and picks its viewport from the mirror's `presentation` (see Calibration below).
- Fog (T007, ADR 0012): the mask is an offscreen canvas the size of the map, derived from the scene's base PNG + op log, never received as pixels while editing. `fogRaster.ts` — `FogRaster<Base>` (`reset(base | null)`, `fillAll`, `fillRect`, `fillRects`, `fillCircle`, `fillPolygon`, `fillStroke`, each with a `FogMode` and an optional `feather`) and `applyFogOp(s)`, the single place that turns a `FogOp` into raster calls; two implementations: `createCanvasFogRaster` (production: `hide` = `source-over` black, `reveal` = `destination-out`; polygons even-odd, rect unions one non-zero path, strokes a round-capped/joined `stroke()` of `lineWidth = 2 × radius`; a feathered op is painted as its own blurred shadow — the shape drawn `SHADOW_SHIFT` (65536) px off the canvas with `shadowOffsetX` bringing the shadow, blurred by `shadowBlur = feather`, back into place; works with both composite operations in every browser, unlike `ctx.filter`) and `createBitmapFogRaster` (a `Uint8Array` alpha, 255 hidden / 0 revealed, pixel-centre coverage, strokes as capsules per segment, feather ignored — the hard edge is where a feathered edge crosses 50 %; `isHidden(x, y)`, `hiddenFraction()` — the unit-test double and, later, the "token under fog" query). `geometry.ts` — pure point / segment / rectangle / polygon containment, distance and intersection helpers. `fogSnap.ts` — `snapShapeToCells(shape, grid, map)`: the grid cells a shape touches (positive-area overlap with the cell shrunk by `SNAP_EPSILON` = 0.001 px, so an edge on a grid line does not spill into the neighbour), clipped to the map, runs per row merged, as one `rects` shape or null. `fogGesture.ts` — the fog tools' pointer state machine (see the DM layout section). `wallGesture.ts` — the wall and door tools' pointer state machine (T102, ADR 0025): `reduceWallGesture(state, event, config) → { state, segment? }` over `down` / `move` / `up` / `double` (each a map-pixel point plus `shift`) and `cancel`, with `config` = `{ tool: WallKind, grid | null, snapThreshold, minDrag }` in map pixels. Every placed point goes through `snapWallPoint` (the nearest grid corner when a grid is given, the point is within `snapThreshold` of it and `shift` is not set; else the point itself). **wall**: `idle` → `drawing(vertices)` on a press (the first vertex); each further press adds a vertex and commits the segment from the previous one (`{ kind, x1, y1, x2, y2 }`), as does a release that travelled at least `minDrag` from its press (a drag draws one segment); a vertex within `minDrag` of the last is ignored; `double` ends the polyline unless its own press placed a vertex (two quick clicks on two corners, or a quick fresh start, are kept), leaving `idle` with `endedAt` so the press and release the browser sends after a double-click start nothing; `cancel` ends it at once. **door**: `idle` → `dragging(start)` on a press, one closed door from the snapped press to the snapped release when they are at least `minDrag` apart. `wallGesturePreview(state)` is the live segment (last vertex or drag start → pointer). A state of the other tool's shape is treated as idle. `fogMask.ts` — `createFogMaskUpdater(raster)`: `update(scene, base)` returns `ready` (incremental: only ops past the history index it has applied are drawn; or a rebuild from the base when the map, the base or the log's past changed), `bridged` (the base changed by compaction but its PNG has not arrived/decoded: the pixels are already right, so keep them, apply new ops, rebuild once it lands) or `waiting` (a base this window never had: fully fogged, the safe default); `bakeFogMask(scene, baseBlob, opCount)` renders base + prefix to a PNG Blob for compaction; `rotateFogMask(baseBlob, size, degrees, { decode?, createCanvas?, encode? })` (T017, ADR 0021) draws the decoded base turned onto a canvas of the turned size — `translate` to `rotatedImagePlacement`, `rotate`, `drawImage` at the old size — and encodes it again; a quarter turn about integer sizes maps pixel centres onto pixel centres, so nothing is resampled, and the placement is the one the stage uses for the image, so mask and image turn identically (the deps are injectable: the unit test drives it with a software 2D context and checks pixels). `useFogMask.ts` — one canvas per stage, updated in a layout effect, with an `onDraw` callback that `batchDraw`s the Konva layer; the updater resizes the canvas when the scene's size changes (a rotation), which forces a rebuild from the (new) base. DM composites the mask at 50 % alpha, player at 100 %. A brush drag never touches the mask until release: the in-progress stroke is a Konva node punched through the fog layer (`fogOverlay`), so dragging costs one overlay redraw per frame whatever the map size, and the committed op is one `fillStroke` on the mask (about 2 ms on a 4096 × 2048 mask in headless Chromium, see `backlog/T008.md`).
- Vision maths (T104, ADR 0026): `visibility.ts` — pure (no DOM, no Konva), shared by both windows: T106 reveals what a dropped token sees, T107 draws what every token currently sees. `blockingSegments(walls)` → `Segment[]` (`{ a, b }` points: every wall and every closed door, through `isBlocking` and `segmentPoints`, so `map/` still reads no wall endpoint by hand); `visionRadiusPx(visionCells, cellSize)` (the product; 0 unless both are positive and finite); `visibilityPolygon(origin, radiusPx, segments, bounds)` → flat `[x0, y0, …]` in map pixels, in angle order round the origin, every vertex on the map. The algorithm is an angular-sweep raycast: rays `ANGLE_EPSILON` (1e-5 rad) either side of every segment endpoint and map corner inside the radius, one to every point where a segment or a map edge crosses the radius circle, and `RADIUS_STEPS` (64) at fixed angles; each ray's nearest hit — a segment, the map's edge (the bounds are four implicit segments, met by a slab test) or the radius — is a vertex, and the vertices are sorted by angle with exact duplicates dropped. Candidates are the finite, non-zero-length segments whose nearest point lies between `ON_SEGMENT_EPSILON` (1e-3 px) and the radius: a segment through the origin blocks nothing, so a token centred on a wall line sees both sides. They are binned by the angle they subtend from the origin (256 bins with one bin of margin; a segment subtending more than 0.9π goes in every bin), nearest first, and a ray stops testing once the next candidate starts beyond its best hit. A ray within a sine of 1e-9 of a segment's direction slides past it (an edge-on wall blocks nothing); a ray through a shared endpoint hits (1e-9 slack on the segment parameter), so collinear walls leave no gap. No radius, an origin that is not a finite point on the map, or an empty map give `[]`. The output depends only on the input values, not on segment order, so both windows compute identical polygons.
- Currently visible and the dim (T107, ADR 0026): `visibleArea.ts` — pure, shared by both windows, nothing stored or synced: `visiblePolygons(scene, segments?)` (one `tokenVisionPolygon` per `seeingTokens(scene)` entry, hidden ones included, in document order; a token that sees nothing adds none; `NO_VISIBLE_POLYGONS` when there are none), `dimActive(scene)` (= `mapUsesVision`) and `createVisiblePolygonsMemo(compute?)` (a one-entry cache keyed on the blocking segments — re-read only for a new walls array — each seeing token's `x`, `y`, `size` and `vision`, the cell size and the map's size: a fog op, a blind token's edit or a snapshot of equal arrays returns the same array; a drag changes none of them, since the store moves a token on the drop). `MapStage` keeps one memo per stage and, while `dimActive`, renders the **dim layer** (name `dim`, non-listening) directly beneath the tokens: `dim-shade`, a black `Rect` over the scene at `DIM_ALPHA[gridView]` (`dm` 0.25, `player` 0.6), then each polygon as a closed `Line` named `dim-visible` with `destination-out` (clearing the shade in the layer's own canvas, so overlaps are harmless), then `dimOverlay`. On the player the opaque fog above it leaves the dim visible on revealed pixels only; tokens are above it, so a token on dimmed ground is drawn at full strength (the fogged-cell rule is unchanged). Without vision the layer is not rendered, so a manual-fog map's canvases and pixels are exactly as before. The wrapper reports `data-dim` (`true` | `false`) and `data-dim-polygons`.
- Calibration (T006, ADR 0011): the player view's mode is `presentationMode(presentation)`. **calibrated** — stage scale locked to `lockedScale(pxPerInch, cellUnit, scene.grid.cellSize)` so one cell is `pxPerInch * cellInches` CSS px whatever the image resolution, centred on the DM's pan centre (`resolvePlayerView` + `playerStageTransform`; the map's centre until the DM drags the viewport rectangle). **overview** — the DM's override: fit to window plus a "not to scale" badge (`data-testid="player-overview-badge"`). **uncalibrated** — fit to window. **calibrating** — the ruler screen: a plain `div` square of exactly `target` CSS px (`data-testid="calibration-target"`, `data-size-px`) with the unit label, instead of the map. Konva and the DOM both draw in CSS px, so the square and a calibrated cell agree at any device pixel ratio. The DM stage keeps free pan/zoom.
- Player view control (T009, ADR 0014): the stage is rotated by `presentation.rotation` (a `Viewport.rotation`; fitted maps are fitted to the rotated window, so a quarter turn fits the map's width to the window's height). The idle title and the splash content are wrapped in a `Rotated` box (CSS `transform: rotate(...)`, width and height swapped for a quarter turn) so text reads the right way up for the players. **Blackout** (`presentation.blackout`) is an opaque black `div` over everything (`data-testid="player-blackout"`, z-index 20); **splash** (`presentation.splash`) is a black `div` over the scene (`player-splash`, z-index 10, `data-splash-kind` `image` | `title` | `default`) showing, in that order of precedence (T015, ADR 0019): the campaign's splash image (`player-splash-image`, from the mirror's asset for `splashImageAssetId`, object-fit contain; the title as the placeholder until it has arrived); the campaign name (`player-splash-title`) when `splashTitleCard` is set; else the default artwork (also `player-splash-image`, `src` = the bundled `src/assets/splash-default.png` imported by URL — a static asset of the same origin, so the render-only player needs no storage and no asset message for it). The idle screen (no active map, splash down) still shows the campaign title. Both are DOM layers, not stage changes: they appear the instant the message lands and the stage underneath keeps its fog mask warm for when they lift. Priority, top down: blackout > ruler screen (replaces the scene and hides the splash) > splash > scene / idle title.

## Storage
- Dexie (IndexedDB), database `tablemap`: `campaigns` (one JSON document per campaign = metadata + `SharedState`), `assets` (map images, fog-mask PNGs, token images as Blobs, keyed by `AssetId` and owned by a `campaignId`), `settings` (last opened campaign; per-display calibration under `calibration:<displayKey>`; the per-display player view rotation under `rotation:<displayKey>` — T019, ADR 0023; the `cellUnit` preference — ADR 0011). Blobs are never serialised into the document; documents reference them by id. See ADR 0007. Calibration and the per-display rotation are deliberately *not* in the campaign document: they belong to the TV, apply to every campaign, and must not travel in exports. The DM window's own UI state (the sidebar tab and whether the sidebar is collapsed) is in `localStorage` (`tablemap.dm.tab`, `tablemap.dm.sidebar`), not in the database: it is neither campaign nor display state.
- Autosave is a debounced subscription on the DM store (`state/autosave.ts`), started by the `/dm` route and flushed on unmount / `pagehide`. Load-on-start opens the last campaign (or creates "Untitled campaign").
- Every document carries `schemaVersion` (currently 10: v1 → v2 adds `MapScene.backgroundColor`, ADR 0009; v2 → v3 turns the single grid style into `grid.dm` + `grid.player`, ADR 0010; v3 → v4 adds the fog log `fogOps` + `fogOpsFrom`, ADR 0012; v4 → v5 changes no data — the fog op vocabulary grew (`stroke`, `rects`, `feather`), so v4 builds must refuse v5 documents rather than call them invalid, ADR 0013; v5 → v6 adds `SharedState.splashImageAssetId` (null), ADR 0014; v6 → v7 adds `SharedState.splashTitleCard` (false: older campaigns without a splash image switch from the title card to the default artwork, like new ones), ADR 0019; v7 → v8 adds `MapScene.imageRotation` (0: older maps were always drawn as stored), ADR 0021; v8 → v9 adds `MapScene.walls` (`[]`: no map had walls before T101), ADR 0024; v9 → v10 adds `Token.vision` (0) to every token and `MapScene.visionDim` (`auto`) to every map — nothing had vision before T105, and `auto` dims nothing while no token sees, so older maps look as they did — ADR 0026); `migrateCampaign` runs the `MIGRATION_STEPS` chain forward on load and refuses newer documents. Dexie `version(n)` is only bumped for index changes.
- Map images are written once at import (`putAsset`, kind `map-image`) and referenced by `MapScene.imageAssetId`; duplicating a map shares the image, so an asset is deleted only when the last map referencing it is removed (`mapActions.remove`).
- Token images (kind `token-image`) are written by `tokenActions.addImage` and referenced by `Token.appearance.assetId`; tokens themselves are part of the scene in the document (T010). Removing the token (or its map) deletes the image once nothing references it; a duplicated map's tokens share the originals' images.
- Fog masks (kind `fog-mask`, PNG) are written by compaction of a map's fog log (`fogActions`, ADR 0012) and by map rotation (`mapActions.rotate`, T017, ADR 0021: the base drawn turned onto a canvas of the turned size by `map/fogMask.ts: rotateFogMask` and stored as a new asset before the `map/rotate` op is dispatched) and referenced by `MapScene.fogMaskAssetId`; the previous base is deleted once nothing references it. A map's fog therefore persists as the base PNG plus the ops since it in the document; a map that has never been compacted has only the ops. Duplicating a map copies the base Blob under a new id. A map's image is never rewritten by rotation: `MapScene.imageRotation` says how far to turn the stored asset when drawing, and travels in the document (and so in exports) while the asset stays as imported.
- The splash image (kind `splash-image`) is written by `splashActions.setImage` and referenced by `SharedState.splashImageAssetId`; choosing another or clearing it deletes the old one unless something else references it. The title-card choice (`SharedState.splashTitleCard`) is plain document state and travels in exports; the default splash artwork is a bundled static file (`src/assets/splash-default.png`), not an asset: it is never stored, exported or sent over the channel (T015, ADR 0019). The player view's pan centre, rotation, blackout and splash state are session-only presentation (ADR 0014): not in the document, not in settings.
- Walls and doors (T101, ADR 0024) are plain document state in `MapScene.walls`: saved by autosave like any op, in every export's `campaign.json`, and never an asset (`referencedAssetIds` ignores them).
- Vision fields (T105, ADR 0026) — `Token.vision` and `MapScene.visionDim` — are plain document state too: autosaved, in every export's `campaign.json`, never an asset; `duplicateMapScene` copies both.
- Export/import (T012, ADR 0017): one JSZip bundle per campaign — `campaign.json` (an envelope with a format marker and version, the stored document unchanged, and an asset manifest) + `assets/<index>-<kind>.<ext>` files with generated, OS-safe names. Import validates the envelope and manifest paths, runs the same `migrateCampaign` chain as a load, and writes the campaign and its Blobs in one transaction, never overwriting: clashing campaign / asset ids get fresh ids with references rewritten. Only assets the document references are exported; calibration and other settings never are (they belong to the TV). See `state/campaignArchive.ts` above.
