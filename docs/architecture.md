# Architecture

Local-first TypeScript SPA. No backend. Ships as static files; runs offline once loaded.

## Windows & sync
- Routes: / campaign manager, /dm DM view, /player player view. Hash router (`createHashRouter`) so static hosting and file:// URLs work. Route table lives in `app/src/routes.tsx`; path constants in `app/src/routePaths.ts` (dependency-free so any module can import them). `/dm` mounts `dm/DmRoute.tsx`, which opens a campaign from storage (load-on-start) before rendering `DmView` and runs autosave while mounted; `/` mounts `CampaignManager.tsx` (list, create, open, rename, delete).
- DM view opens /player with window.open (named window `tablemap-player`, `popup` feature for a chrome-less window). The DM window retains the handle in a controller (`app/src/dm/playerWindow.ts`, pure logic with injectable deps; React binding `usePlayerWindow.ts`) and uses it to focus, full-screen and close the player window. Re-clicking "Open" focuses the existing window instead of spawning another. The hook polls the handle (500 ms) for closed/fullscreen changes because no cross-window event survives the popup's own navigation.
- Fullscreen: the DM toggle calls `requestFullscreen` on the player document via the handle. Browsers only honour that from a user gesture in the *target* window, so the request is often denied (it is in headless Chromium). The DM view then shows a hint, and the player view offers an in-window fallback: press **F** or double-click. See ADR 0005. The OS puts the window on the TV (Window Management API where available, manual drag as fallback).
- Player/DM boundary: `src/player/**` must never import from `src/dm/`. Enforced by an ESLint `no-restricted-imports` rule scoped to `src/player` and by a unit test (`src/player/boundary.test.ts`).
- DM layout (`DmView`): top toolbar (player-window controls), left sidebar (campaign name, `dm/MapPanel.tsx`, tools), main canvas area (`dm/DmCanvas.tsx`, the Konva stage for the active map with wheel zoom / drag pan and a **Fit** button). The whole DM view is a drop target for image files (`data-dragging` + an overlay while a file is over it); the file picker lives in the map panel. Import UI state (queue, "Importing…", last error) is `dm/useMapImport.ts`.
- **Single source of truth is the DM window Zustand store.** The player window is a dumb mirror: it applies sync messages received over a BroadcastChannel and renders. It never mutates state. Message schema lives in app/src/state/sync.ts (typed, versioned). Full-state snapshot on player connect; deltas after (fog ops are sent as operations, never bitmaps). Binary assets (map images) are pushed by the DM as `asset` messages on the same channel (ADR 0008); the player never reads storage.

### State & sync modules (`app/src/state/`)
- `model.ts` — scene-level data model: `MapScene` (id, name, `imageAssetId | null`, `backgroundColor`, size, `grid`, `fogMaskAssetId`, tokens, annotations), `GridSettings`, `Token`, `Annotation`, `AssetId`, `AssetKind`, `SCHEMA_VERSION` (2, ADR 0009), plus structural type guards. Binary data is referenced by `AssetId`, never embedded.
- `shared.ts` — `SharedState` (the only state the player ever sees: `campaignName`, `maps`, `activeMapId`) plus `SharedOp`, the discriminated union of operations that change it (`campaign/set-name`, `campaign/replace`, `map/add` (with optional insert index), `map/remove` (clears `activeMapId` if it pointed there), `map/rename`, `map/set-active` (ignored for unknown ids)), and the pure reducer `applyOp`. Both windows run the same reducer. `SharedState` is also the body of the persisted campaign document, so it must stay plain JSON. Later tasks extend the state and add op kinds here.
- `maps.ts` — pure scene helpers: `createImageMapScene`, `createBlankMapScene` (size in cells × cell size, colour), `duplicateMapScene` (deep copy, shares the immutable image asset, takes the id of a *copied* fog mask), `findMap`/`activeMap`, `sceneAssetIds`/`referencedAssetIds`, and `assetIdsForPlayer` (active map's assets first, then every other map's).
- `mapActions.ts` — the DM's map operations over a store + database: the import pipeline `importMapImage(db, campaignId, file, { measureImage })` (validate PNG/JPEG/WebP by MIME or extension → decode for size (`measureImageInBrowser`: `createImageBitmap`, `Image` fallback; injected in tests) → `putAsset` → `createImageMapScene`; throws `MapImportError`, writes nothing on failure) and `createMapActions(store, db)` → `importImage` (add + activate in one dispatch), `createBlank`, `duplicate` (copies the fog-mask Blob, inserts after the original, activates the copy), `rename`, `remove` (then deletes assets nothing references any more — image assets are shared by duplicates), `setActive`.
- `assetCodec.ts` — `blobToBase64` / `base64ToBlob` for `asset` messages.
- `store.ts` — the DM store (`createTableStore`, app-wide `tableStore`, `useTableStore` hook). Shared state changes only via `dispatch(...ops)`, which applies the reducer, bumps `seq` by one per dispatch and notifies `onOps` listeners. `campaignId` (DM-only) names the persisted document the shared state belongs to; `openCampaign(campaign)` sets it and applies `campaign/replace` in one commit, `closeCampaign()` clears it. **`src/player/**` may not import this module** (ESLint `no-restricted-imports` + `boundary.test.ts`).
- `sync.ts` — the protocol (ADR 0006, ADR 0008): `PROTOCOL_VERSION`, `SYNC_CHANNEL_NAME`, message types `hello` / `snapshot` / `delta` / `asset` (`{ id, kind, mime, data: base64 }`, unsequenced), constructors, `encodeMessage` (JSON string) and `decodeMessage`/`validateMessage` (never throw; reject other versions, unknown types and bad shapes).
- `transport.ts` — `SyncTransport` interface (`post`, `onMessage`, `close`). `createBroadcastTransport` wraps a BroadcastChannel; `createMemoryHub` is the in-test replacement with the same fan-out (never echoes to the sender); `createNullTransport` is used where BroadcastChannel is missing.
- `mirror.ts` — the player-side `MirrorState` (`connecting | synced`, `seq`, `shared | null`, `assets: Record<AssetId, Blob>`) and the pure `reduceMirror(mirror, message)`: snapshots always replace; a delta applies only if `seq === mirror.seq + 1`; stale/duplicate deltas are ignored; a gap, or a delta before any snapshot, sets `resync` so the caller re-requests a snapshot. `asset` messages are decoded into `assets` whenever they arrive (undecodable data is ignored); after every snapshot/delta, assets the state no longer references are dropped.
- `dmSync.ts` — `startDmSync(store, transport, { assets? })`: on start sends `hello(dm)` + a snapshot (so already-open players catch up), answers every player `hello` with a snapshot, and forwards each dispatch as one `delta`. Ignores all other traffic; nothing received can mutate the DM store. With an `AssetSource` it also pushes every referenced asset not yet sent this session (queued, one at a time, `assetIdsForPlayer` order) after the snapshot/delta, and re-sends all of them on a player `hello`.
- `playerSync.ts` — `startPlayerSync(mirror, transport)`: sends `hello(player)` on start and whenever `reduceMirror` asks for a resync; writes decoded messages into the mirror. **The player only ever sends `hello`.**
- React bindings: `dm/useDmSync.ts` (DM view; passes an `AssetSource` backed by `getAsset`) and `player/usePlayerSync.ts` (player view) create the transport inside an effect so StrictMode's double mount gets a fresh channel; both views accept an injected `createTransport` for tests. `PlayerView` exposes `data-sync-status` / `data-sync-seq` / `data-active-map-id` on its root for e2e assertions.
- Reconnect: a reloaded player window is simply a new endpoint; its `hello` fetches a full snapshot and deltas resume from that `seq`. A player opened before the DM stays `connecting` until the DM's start-up snapshot arrives.

### Persistence modules (`app/src/state/`, ADR 0007)
- `campaign.ts` — the persisted document `Campaign = { schemaVersion, id, name, createdAt, updatedAt, state: SharedState }`, `CampaignSummary` (what the manager lists), `newCampaign`, `isCampaign`, and `migrateCampaign` (never throws; brings older documents to `SCHEMA_VERSION`, reports `newer-schema` / `invalid`).
- `db.ts` — the Dexie database `TableMapDb` (`getDb()` is the app-wide instance; tests construct their own with a unique name). Tables: `campaigns` (documents, JSON only; indexed by `name`, `updatedAt`), `assets` (`{ id, campaignId, kind, blob }` — map images, token images, fog masks as Blobs), `settings` (key/value: last opened campaign; later, per-display calibration).
- `persistence.ts` — async functions over a `TableMapDb`: `listCampaigns`, `createCampaign`, `loadCampaign` (migrates; throws `CampaignLoadError` for corrupt/newer documents), `saveCampaign`, `saveCampaignState` (what autosave calls; false if the campaign was deleted meanwhile), `renameCampaign`, `deleteCampaign` (also deletes its assets and the last-opened pointer), `putAsset`/`getAsset`/`deleteAsset`/`listAssetIds`, `getLastCampaignId`/`setLastCampaignId`, and `resolveStartupCampaign` (last opened → most recently updated → new "Untitled campaign"; unreadable documents are skipped).
- `autosave.ts` — `startAutosave(store, save, { debounceMs })`: subscribes to the DM store; any change to `shared` while `campaignId` is set schedules a write of the latest state after the debounce (default 400 ms); bursts coalesce; writes are serialised; opening another campaign or closing flushes first; `flush()`/`stop()` for unmount and `pagehide`. Pure logic, no IndexedDB.
- `session.ts` — `openStoredCampaign(store, db, id)` and `bootstrapCampaign(store, db)` (load-on-start; no-op when a campaign is already open; concurrent calls share one promise so StrictMode's double effect cannot create two default campaigns).
- `src/player/**` may not import `db`, `persistence`, `autosave` or `session` either (same ESLint rule + boundary test): the player never touches storage.

## Rendering (`app/src/map/`, shared by both views; imports neither `dm/` nor the DM store)
- Konva stage with layers bottom-to-top: map image -> grid -> tokens -> annotations -> fog.
- `MapStage.tsx` — the react-konva stage. Props: `scene`, decoded `image` (or null), container `size`, `viewport` (`{ x, y, scale }` = stage transform), `interactive` (wheel zooms around the pointer, dragging the stage pans; the new viewport is reported via `onViewportChange` — the caller owns it), `showGrid`. Layer 1: a `Rect` in `scene.backgroundColor` (all of a blank map) under the `Image`; layer 2: the grid as one `Shape` (`strokeScaleEnabled=false` so lines stay 1 px at any zoom). The wrapper exposes `data-map-id`, `data-map-name`, `data-image-status` (`none | waiting | loading | loaded | error`) and `data-scale` for tests.
- `viewport.ts` — pure math: `fitToView` (contain + centre with padding), `zoomAt` (keeps the map point under the pointer fixed; scale clamped to 0.05–8), `wheelZoomFactor`, `panBy`. `grid.ts` — `gridLinePositions`/`gridLines` from `GridSettings` (offset wrapped into the first cell).
- `useImageElement.ts` — Blob → object URL → decoded `HTMLImageElement` (revoked on change/unmount). `useContainerSize.ts` — ResizeObserver-backed element size.
- DM (`dm/DmCanvas.tsx`): reads the active map's Blob from the database (`dm/useAssetBlob.ts`, which also provides object URLs for the panel thumbnails), fits the viewport whenever the active scene changes, then leaves pan/zoom to the user. Player (`PlayerView`): takes the Blob from the mirror's `assets`, always fits the map to the window (calibration-locked zoom is a later task) and shows the idle campaign title when no map is active.
- Fog: offscreen canvas mask, black-filled; reveal ops drawn with globalCompositeOperation destination-out (radial-gradient brush for feathering). DM composites the mask at ~50% alpha, player at 100%. Mask persisted as PNG blob; undo via bounded operation log with periodic snapshot compaction.
- Calibration: player stage scale fixed to pxPerInch / gridInchesPerCell; DM stage free pan/zoom.

## Storage
- Dexie (IndexedDB), database `tablemap`: `campaigns` (one JSON document per campaign = metadata + `SharedState`), `assets` (map images, fog-mask PNGs, token images as Blobs, keyed by `AssetId` and owned by a `campaignId`), `settings` (last opened campaign; later per-display calibration). Blobs are never serialised into the document; documents reference them by id. See ADR 0007.
- Autosave is a debounced subscription on the DM store (`state/autosave.ts`), started by the `/dm` route and flushed on unmount / `pagehide`. Load-on-start opens the last campaign (or creates "Untitled campaign").
- Every document carries `schemaVersion` (currently 2: v1 → v2 adds `MapScene.backgroundColor`, ADR 0009); `migrateCampaign` migrates forward on load and refuses newer documents. Dexie `version(n)` is only bumped for index changes.
- Map images are written once at import (`putAsset`, kind `map-image`) and referenced by `MapScene.imageAssetId`; duplicating a map shares the image, so an asset is deleted only when the last map referencing it is removed (`mapActions.remove`).
- Export/import: JSZip bundle — campaign.json (the same document) + assets/ blobs. Importers run the same migration.

react, react-dom, react-router-dom, konva, react-konva, zustand, dexie, jszip, nanoid.

## Testing strategy
- Unit (Vitest): state slices, sync protocol encode/decode, fog op math, grid/calibration math, persistence round-trips (fake-indexeddb). Sync is tested end-to-end without a browser by wiring `startDmSync` and `startPlayerSync` through `createMemoryHub` (`src/state/syncDrivers.test.ts`).
- E2E (Playwright): multi-page tests — one context, DM page + player page — asserting the player render reacts to DM actions (fog reveal, blackout, ping, scene switch). Visual sanity via screenshot assertions on the fog layer. The player page is obtained by clicking "Open player view" and awaiting `context.waitForEvent("page")` (see `e2e/player-window.spec.ts`). `e2e/sync.spec.ts` covers live updates, snapshot-on-open, player reload and a player opened before the DM.
- Unit tests that need source text (e.g. the player/DM boundary test) use Vite's `import.meta.glob(..., { query: "?raw" })` rather than Node `fs`, so no Node typings are needed.
- `src/test/setup.ts` (Vitest `setupFiles`) installs `fake-indexeddb/auto`, so components that touch storage work under jsdom. Tests that store Blobs (`persistence.test.ts`, `session.test.ts`, `mapActions.test.ts`) run under `// @vitest-environment node`: jsdom's `Blob` is not structured-cloneable by fake-indexeddb, Node's is. Every persistence test uses a uniquely named `TableMapDb` and deletes it afterwards. jsdom's Blob also lacks `arrayBuffer()`/`text()`; `src/test/blob.ts` reads Blobs via `FileReader` in jsdom tests.
- Konva under jsdom: `vite.config.ts` aliases the bare `konva` import to `konva/lib/index.js` (its Node entry requires the native `canvas` package) and inlines `react-konva` so the alias applies to it; `setup.ts` stubs `HTMLCanvasElement.prototype.getContext("2d")` with a no-op context. Component tests can therefore mount `MapStage` and assert on the scene graph, data attributes and wheel handling; what is actually painted is asserted in e2e by reading pixels from the stage canvas.
- `e2e/persistence.spec.ts` covers the reload-restores-campaign criterion and the campaign manager against real Chromium IndexedDB (reading the database directly via `page.evaluate` to wait for autosave).
- `e2e/maps.spec.ts` covers import (file picker and drag-drop via a `DataTransfer` built in the page), the Blob in IndexedDB, re-render after reload, the player showing the active map (pixel colour of the stage canvas, polled because Konva draws on the next animation frame), scene switching, player reload, blank maps, rename/duplicate/delete and wheel/drag on the DM canvas. Fixture: `e2e/fixtures/map.png`, a generated 320×200 PNG, orange (230,120,20) with an 8 px white border; Vite serves it at `/e2e/fixtures/map.png` in dev.
